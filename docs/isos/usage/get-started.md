# First use: IsOS and MuJoCo

[中文](../../../docs_cn/isos/usage/get-started_cn.md)

## Follow the running system

**Works today:** New graphs use `0.1.0` and registered `@v0.1` types. Known safe `1.0.0` graphs remain readable and require explicit migration before editing after Apply. Setting selectors, shared event fields, and EGIA integration are [later milestones](../maintenance/roadmap.md). Read status first, then logs for the same step; a startup line records a transition, while status reports the live state.

1. Install IsOS and run plain `isos`. It creates missing development configuration and graph, starts the API on 16000 and IsosUI on 16001, and opens the browser. EOS, EGIA, and MuJoCo remain stopped. Running `isos` again reuses the workbench. `isos init` performs only the file initialization and exits.

```sh
isos
```

2. Build EOS, EGIA, and IsosUI in their owning repositories; set `paths.aether_bin_dir`, `paths.egia_bin_dir`, and `paths.ui_dist` in the IsOS checkout's `config/isos.toml`. Run `isos version check` (`--json` for scripts). Fix each reported missing executable or setup mismatch before trying to start hardware. EGIA may still report blocked while the Rust EOS gateway is unfinished. `isos serve` starts the workbench without opening a browser; `isos open` starts it if needed. `isos serve --ui-live` is for frontend development only.

For a new `0.1.0` draft, Graph shows the saved revision. Validate, then Apply with that revision. A first API PUT on a missing graph uses an explicit empty revision (`"revision":""`); after `isos init` has saved the starter, use its actual SHA-256. CLI Apply takes `--revision <saved-sha256>` for the saved starter or later edits, and `--revision ""` only when the destination file is absent. An unavailable owner reader blocks Apply and leaves the draft bytes unchanged.

3. Build the MuJoCo simulator and stage a `0.1.1` bundle using its repository's `tools/build-backend-bundle.py`; set `MUJOCO_ROOT` to the matching runtime. Link the exact verified bundle. Preview `sim-hardware` in Graph or with `isos pkg preview-set`. The starter has EOS process and dispatcher nodes, but no hardware package. The P02 `0.1.0` preset adds the MuJoCo process, generic EOS camera, base, manipulator, base/arm primitive bindings and camera gate; it does not add a Vision node. Select `pick-place` or `navigation` and camera/base/manipulator IDs available for that scene, review the draft, Validate, then Apply in Graph. Installing or linking alone never changes the graph. The P02 IsOS catalog admission is already active. For P03 selector options, request `POST /api/isos/v1/node-options` after each draft change; use its available scene and device IDs, set each generic adapter's `device_id` and `simulator_node` together, and Apply only with the latest saved revision. An unavailable saved ID remains visible but blocks Apply. [Package operations](packages.md#p03-selection-workflow) cover CLI preview, the selector flow and exact negative checks:

```sh
isos pkg link island/mujoco-sim 0.1.1 /absolute/path/to/bundle --manifest /absolute/path/to/bundle/release.json
isos pkg node-sets
```

4. After Apply, run `isos run`; it stays attached. In another terminal, read `isos status --json` for the saved and active revisions, process readiness and last error. Then read `isos logs all --level info` for the startup sequence. The current IsOS start line marks a boot attempt; status confirms readiness. On a MuJoCo or loadable-adapter package load failure, read `isos logs packages --level warn` first: its `package_id`/`package_version` identify the pinned release, while `run_id` and `correlation_id` group a manager preflight failure; then inspect the command error for the specific repair. EOS and MuJoCo sources explain child startup. Use `isos logs eos --level warn` or the IsosUI Logs panel to investigate a specific failure. Log files are under the private data root's `logs/<deployment>/`; [configuration and log rules](../interfaces/configuration.md) explain paths, filtering, rotation and cursors. **P06 first use:** Keep `isos status --json` as the live readiness check. For a failed Validate, Apply or Run preflight, read the first `packages` or `isos` error under the manager-session `run_id` and the request `correlation_id`; its safe typed fields carry the exact package pin and any verified receipt digest. After accepted Start, read one `deployment_starting`, the selected EOS child `eos_ready` and EGIA owner-ready event where enabled, then `deployment_ready` under the newly allocated deployment-run ID. Use `isos logs eos --level warn` and the same run/correlation to inspect child transitions and the terminal stop. EOS raw simulator diagnostics live in the separate private `owner/eos/` directory. A package-load detail and preflight summary from one failed request share a correlation ID; if the first Start fails, retrying after repair uses a fresh run ID. A malformed graph pointer is omitted from the safe event while the failure summary remains. The [shared event contract](../interfaces/events.md) defines the JSONL bounds and source mapping. P07 adds rotation-safe first-event cursors; use `isos logs all --current` after status to see the pinned first event and subsequent retained lines.

5. Ctrl+C stops the attached deployment. `isos deployment stop` stops only the graph; `isos stop` also stops independent services, UI, API, and manager. Repeated stops succeed. After stopping, confirm `isos status --json` says stopped, then read warning/error logs if the stop was abnormal. A clean stop does not need a flood of per-tick messages.

Run rechecks the exact graph revision, configured executables, package, scene, and assets. EOS starts and owns its MuJoCo child. Installing a package, changing a configured build path, or editing a draft does not alter an active deployment; Apply and Restart explicitly. See [package commands](packages.md), [graph fields](../interfaces/node-graph.md), and the [independent services contract](../interfaces/services.md).

For an applied `0.1.0` graph, Run compares the revisioned generated files with a fresh owner render before launch. If a configured EOS or EGIA binary changes, `isos init` reports the stale launch input and preserves the immutable snapshot. Restore the pinned binary or create a new graph revision and Apply before running again.

**P04 generated configuration first use:** Select installed EOS and EGIA releases, set `paths.egia_defaults_dir` and `paths.egia_factory_defaults_dir` to that EGIA distribution's component and factory default trees, verify the exact MuJoCo package pin, then Validate and Apply the saved graph revision. IsOS publishes a private generation selected for that exact revision. Inspect the saved revision entry in `data/generated/<deployment>/selection.json`, its durable `v2/required/<revision>.json` marker, and the selected `v2/<revision>/<generation>/manifest.json`; the hashes must match the saved graph and selected installed inputs. A missing selection after P04 Apply blocks Run rather than using an older G03 snapshot. The selected leaf contains EOS `graph.json` and, when EGIA is enabled, complete EGIA startup configuration including models, prompts, missions and safety gate. IsOS passes the leaf's absolute `egia/` path through `EGIA_ETC` and `--etc`. Until EOS has its complete gRPC gateway, test this with an EGIA setup stub and keep EGIA runtime disabled. After rebuilding a selected binary or changing installed defaults, explicitly Apply the same saved revision to select a new generation, then Restart. A failed Apply or Run reports a sanitized `generated_*` code and leaves the active deployment unchanged. Keep secret values in the manager environment; configure only `env_from` names and check that a missing name for any intended child fails before any active child is stopped. Values go only to their named child at spawn. Generated files stay in the private IsOS data root, never in either source checkout. [Configuration and preflight](../interfaces/configuration.md#p04-generated-configuration-and-launch-preflight-implemented-in-isos) lists the frozen fields and errors.

If new children fail during a restart, IsOS stops that attempt and restarts the previous process specifications under the previous active revision. If the previous children cannot be restored, status reports a degraded deployment and the restart error.

**P05 reader-feature preflight:** After selecting the EOS and optional EGIA builds and exact MuJoCo package, run `isos version check --json`. Inspect each enabled core's diagnostics, then Validate and Apply the draft with its saved revision. Run and Restart recheck the selected graph, binary identities, required features and P04 generation before replacing a child. A missing `@v0.1` type, `mujoco-child-v2` claim, EGIA runtime `managed-config-v1`/`eos-gateway-client-v2` claim or verified package pin blocks admission even when the product version looks recent. For EGIA, select an existing interpreter with `EGIA_PYTHON` or `ISLAND_PYTHON` and the installed module tree before checking; the no-start probe does not create a virtual environment or run `uv sync`. IsOS records the selected interpreter path, resolved target, digest and code inventory, then rechecks them before Restart. Restore a compatible selected build and Apply the same revision again. `compatible_upgrade` remains `null` unless one exact verified release is available and checked against the graph. The [P05 contract](../interfaces/reader-features.md) defines diagnostic fields and failure-before-stop behavior.

## R03 managed control-grant replay

**Local EOS/IsOS R03 replay passed; reviewed PR merges pending.** After Validate and Apply of a `0.1.0` graph, run the managed deployment from a clean `ISOS_HOME`. Check `isos status --json`: `active_revision` must equal the saved graph's exact byte SHA-256, and `run_id` must identify this launch. IsOS must have selected an explicit verified schema-2 V2 generation and created one private run bundle under `run/control-grants/<deployment>/<run_id>/`; a G03 fallback is insufficient. Check only its file names, permissions and verifier run/revision; do not print grant contents or put them in a command line, browser or log. The required selected EOS runtime receives `EOS_CONTROL_GRANTS_FILE`; EGIA receives only `EGIA_EOS_CONTROL_GRANT_FILE` **if selected**, and the supervised bridge receives only `AETHER_BRIDGE_CONTROL_GRANT_FILE` **if selected**. An EOS-plus-config deployment without EGIA or bridge is valid; config receives no grant. [The owner contract](../interfaces/control-grants.md) fixes the exact fields and method scopes.

Use EOS discovery metadata to compare `eos-active-revision` with IsOS `active_revision`; `eos-projection-sha256` is a separate digest. If selected, managed EGIA gRPC movement uses its role grant and that active revision. The operator grant allows bridge `primitive_typed` movement and governed gRPC stop/recovery, not gRPC movement; neither grant comes from a browser. Query a lost reply by its original operation ID. An idempotent Start and automatic child restart retain this run's grants; explicit Restart rotates both, even when graph bytes are unchanged. For a rejection **before** `deployment_starting`, inspect the manager-session `deployment_preflight_failed` event with its request correlation through the legacy `isos` log source and status; `isos logs all --current` may still show the earlier admitted run. Once a candidate run starts, use `isos logs all --current` for its first ready or failure event. Verify that no credential or bearer text appears. A missing, unsafe or stale bundle must fail before writable EOS readiness. The local clean-home replay verified IsOS issuance and delivery against the selected EOS candidate, including real governed gRPC movement and result lookup; reviewed PR merges remain before R03 closes. R05/R06 later qualify MuJoCo physical fencing and safe stop.

The selected EOS `--capabilities` must include exact `managed-control-grants` before Run or Restart; an older binary is rejected during reader preflight while any active child remains running.

### Migrate a saved legacy graph

For an applied `1.0.0` graph, read its saved revision from Graph or `GET /api/isos/v1/node-graph` before editing. A wholly mapped safe graph also shows `legacy_projection` for inspection: its legacy type IDs stay unchanged, while `mappings` lists candidate replacements and `defaults` marks display-only values. Edit the original `graph` and use explicit migration; submitting the projection as a changed graph is rejected without writing. An unmapped old control type stays read-only and reports its exact `/node_type` path before Run. Preview reports exact type substitutions, the full `0.1.0` proposal, and blockers without changing saved bytes or running children:

```sh
isos config migrate --preview --revision <saved-sha256>
```

Review the proposal and resolve owner-reader or package blockers. Then commit **the previewed digest** with both revisions:

```sh
isos config migrate --revision <saved-sha256> --proposed-revision <preview-sha256>
```

A stale source or proposal digest requires a new preview. `isos status --json` then shows the new saved revision and prior active revision until explicit Restart. Unmatched legacy types stay read-only; use the [migration guide](../maintenance/migration.md) to repair them explicitly.

## P07: first event and subsequent logs

Before the first admitted run, use `isos logs all --current --level info --lines 100` or `GET /api/isos/v1/logs?view=current&source=all&level=info`. The manager-session scope pins the first package or Apply failure. After admission, the same request returns the deployment run's first ready or failure event; the anchor appears separately even when source, level, node or correlation filters exclude it. Poll `next_cursor` while the anchor is pending. After Stop or failure, inspect the last admitted run's terminal logs; a new admitted run reports `log_run_changed` on an old cursor. Retained rotation continues the cursor; show `diagnostics` for expiry, collector loss or unavailable anchor, then continue with the new cursor. Check live state with `isos status --json` first; the page explains history. If `run_id_state:unavailable` or `log_scope_unavailable` appears, show the typed outage and do not display a manager-session page. See the [current-run log cursor contract](../interfaces/log-cursors.md).
