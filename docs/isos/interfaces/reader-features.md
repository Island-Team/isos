# P05 reader and feature preflight

[中文](../../../docs_cn/isos/interfaces/reader-features_cn.md)

**Target design — not implemented.** IsOS owns admission of the saved deployment graph, exact package pins and selected core executables before Apply, Run or Restart. EOS and EGIA own the capability identities emitted by their binaries. This contract extends the [version overview](configuration.md#version-admission) and the schema-1 [local API](local-api.md#configured-builds-and-version-readiness); P05 work is tracked in the [0.x roadmap](../maintenance/roadmap.md). Reader compatibility does not itself establish runtime readiness: an enabled EGIA core still needs the EOS gateway health barrier.

## Caller, source of truth and probe

The operator calls `isos version check --json` or the owner-only loopback Graph Validate/Apply and deployment Run/Restart operations. IsOS reads the exact saved graph bytes and revision. For Validate it checks the submitted draft without writing; for Apply it repeats checks under the graph lock immediately before P04 publication; for Run/Restart it checks the saved revision, selected P04 generation and every intended child before stopping or spawning one. Migration preview checks the proposed `0.1.0` graph but never treats a read-only legacy projection as saved bytes. All probes are bounded and start no core runtime.

IsOS resolves the configured `aether-profile` setup reader, the EOS runtime, bridge and config-server from the actual IsOS process specifications, and the selected EGIA setup and runtime when EGIA is enabled. It probes the same executable path and digest that P04 inventories and later launches. A path-only match, an unselected sibling build, a PATH lookup, a product-version comparison or a probe of a different binary cannot admit the child. A changed executable or package receipt between probe, P04 generation verification and spawn invalidates the preflight; Run/Restart fail before active child replacement. The bridge does not read the graph, so its legacy scalar capability identity and required transport features are checked without demanding graph/type arrays.

Each enabled owner setup `identity` keeps schema-1 `core`, `product_version`, `setup_schema_version`, legacy `graph_version` and `node_type_version`, and advertises `supported_graph_versions`, `supported_node_type_versions`, `supported_node_types` and `features`. The arrays contain exact accepted versions and built-in type IDs; `features` contains stable ASCII feature IDs. Verified package contributions are checked in addition to, never impersonated by, built-in `supported_node_types`. The legacy scalars are aliases for older readers and do not override present arrays. The selected runtime child reports `binary`, `product_version`, the same supported arrays where it reads the graph, and `features`; EOS uses `--capabilities`, and EGIA P05 adds a bounded, no-start `egia --capabilities` probe on its selected launcher. The P05 implementation must verify setup and runtime claims independently. A partially present, malformed, empty, duplicated or contradictory version/type array set fails closed. An older identity with all version/type arrays absent may use the validated scalar values as singleton sets only for an actual safe `1.0.0` graph and exact registered `@v1.*` types; it cannot authorize `0.1.0`, `@v0.1` or a feature absent from its explicit `features` list. An array that is present but omits a value never falls back to the scalar.

| Field | JSON type / unit | Purpose, absence and validation |
| --- | --- | --- |
| `supported_graph_versions` | nonempty array of unique strings / — | Exact graph wire versions read by that binary; missing permits only the legacy scalar fallback above. |
| `supported_node_type_versions` | nonempty array of unique strings / — | Exact registered type suffix versions, such as `0.1` and `1.0`; this is necessary but never sufficient to admit a type ID. |
| `supported_node_types` | array of unique full type IDs / — | Exact built-in IDs implemented by this reader. Missing permits only exact types in the frozen safe legacy registry; a contributed type also needs its verified package pin and owner catalog. |
| `features` | array of unique ASCII strings / — | Implemented capabilities of that binary. Missing means the empty set; a required feature then fails. |
| `binary` | stable executable ID string / — | Required for a runtime `--capabilities` reply and must equal the selected role, for example `aether-runtime`; setup identity uses `core` instead. |
| `product_version` | nonempty string / — | Reported release for display and provenance; it is not a reader compatibility predicate. |
| `setup_schema_version` | integer / — | Must equal `1` on setup identity; independent of graph and product versions. |

An EOS setup fixture reply is `{"schema_version":1,"ok":true,"diagnostics":[],"files":[],"identity":{"core":"eos","product_version":"fixture","graph_version":"1.0.0","node_type_version":"1.0","supported_graph_versions":["1.0.0","0.1.0"],"supported_node_type_versions":["1.0","0.1"],"supported_node_types":["eos.hardware.camera@v0.1"],"features":["setup-v1","graph-0.1-reader","catalog"],"setup_schema_version":1}}`. Exact EOS features and all built-in IDs for real binaries are fixed by the EOS companion contract. EGIA's current setup advertises both graph versions but only type version `1.0`, so that alone never admits an EGIA `@v0.1` type. A focused runtime fixture is `{"binary":"aether-runtime","product_version":"fixture","graph_version":"1.0.0","node_type_version":"1.0","supported_graph_versions":["1.0.0","0.1.0"],"supported_node_type_versions":["1.0","0.1"],"supported_node_types":["eos.hardware.camera@v0.1"],"features":["graph-0.1-reader","log-dir"]}`.

## Required set and admission order

IsOS parses the actual graph version and every enabled node's full registered type ID at its JSON Pointer. It first validates graph structure and safe legacy identity, then verifies each exact package receipt, contribution and pin before consuming its type catalog. An unknown future graph retains G01 `unsupported_graph_version`, and an unregistered or unmapped type retains its G01/G03 exact-path diagnostic; P05 `reader_graph_unsupported` and `reader_type_unsupported` apply only to known graph versions and registered types missing from the selected reader set. For EOS, it passes each verified sidecar as the existing repeatable `--node-types <absolute-path>` argument to the exact selected `aether-profile` setup/catalog probe and EOS runtime/config-server probes; `setup catalog` without those flags contains only built-ins. It derives the required graph/type versions and feature IDs from the combined registered owner catalog, node configuration, edges and process role; graph-authored unknown feature strings do not grant capabilities. A suffix match cannot admit an unregistered type or a package-contributed type from a different pin. The MuJoCo process type is contributed by the verified `island/mujoco-sim@0.1.1` package; generic EOS camera, base and manipulator types are built in. Required features are checked against the exact binary that implements them. IsOS checks each enabled setup reader, each graph-reading runtime child, then non-reader transport children, and finally P04 rendered inputs, secrets and readiness prerequisites. Diagnostics are deterministic: saved graph path order, then binary role, then feature ID; the first failure blocks Apply/Run/Restart. Package tamper retains its P01/P02 code and wins before reader mismatch. P04 generated snapshot mismatch wins before an attempted replacement; P05 never repairs it implicitly.

For the `0.1.0` EOS graph, `aether-profile`, `aether-runtime` and enabled `aether-config-server` each need `graph-0.1-reader`, `node-types` and `data-idl`. `aether-profile` also needs `setup-v1` and `catalog`; `aether-runtime` additionally needs the features selected by enabled nodes: `log-dir` when IsOS passes `--log-dir`, `primitive-binding` for a primitive node, `vision-gate` for a camera gate, and `mujoco-child-v2` for `eos.process.mujoco@v0.1`, `eos.process.mujoco@v1.0`, or a verified v2 child launched by `eos.process.backend@v1.0`. The existing fixed `short-paths` EOS process check remains. `aether-http-bridge` needs its declared `vision-ws` transport feature whenever its process is enabled, without a graph reader claim. EGIA setup and runtime requirements are derived only from exact EGIA registered types and their owning feature declarations; until EGIA publishes a verifiable runtime identity, an enabled EGIA process remains blocked. A reader advertising `0.1.0` but not the requested exact `@v0.1` type or required feature is incompatible.

## Typed failure and version report

The schema-1 HTTP envelope keeps `ok:false`, `error` and `data.diagnostics`; CLI emits the same stable code and a sanitized repair message, and `isos version check --json` includes the same diagnostic objects with each core's existing `ready`, `reason` and `action` fields. A P05 diagnostic contains exactly `code`, `path`, `message`, `stage` and `reader`. `reader` has `core`, `binary`, `binary_sha256` (lowercase 64-hex or `null` if the selected file cannot be read), `requested` and `supported`. `requested` contains only applicable `graph_version`, full `node_type`, `feature` and exact `{id,version}` package pin; absent values are `null`. `supported` contains sorted unique `graph_versions`, `node_type_versions`, full `node_types` and `features`; unknown sets are empty arrays. `path` is the exact JSON Pointer of `/version`, a node's `/node_type`, a node's `/package`, or the node/edge setting that requires a feature; a global selected-binary failure uses the exact IsOS process node `/settings/command/0`, or `""` for the setup reader. `stage` is `graph`, `package`, `reader` or `feature`. Stable codes are `reader_identity_invalid`, `reader_graph_unsupported`, `reader_type_unsupported`, `reader_feature_unsupported`, `reader_binary_mismatch`, and `reader_package_pin_mismatch`. `message` names the selected binary and an action, but never raw stderr, secrets, local paths or speculative releases.

For example, a graph reader lacking a required feature returns HTTP `422` with `data` containing `{"diagnostics":[{"code":"reader_feature_unsupported","path":"/cores/eos/layers/interface/groups/gate/nodes/preview/node_type","message":"aether-runtime lacks vision-gate; select a verified compatible build and Apply again","stage":"feature","reader":{"core":"eos","binary":"aether-runtime","binary_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","requested":{"graph_version":"0.1.0","node_type":"eos.interface.camera_gate@v0.1","feature":"vision-gate","package":null},"supported":{"graph_versions":["0.1.0","1.0.0"],"node_type_versions":["0.1","1.0"],"node_types":["eos.interface.camera_gate@v0.1"],"features":["log-dir"]}}}]}` and `error:"reader preflight failed"`. An unreadable or wrong selected executable reports its actual role and `reader_binary_mismatch` before spawn. A malformed identity reports `reader_identity_invalid`, with empty supported sets if the reply cannot be trusted.

`isos version check --json` may include `compatible_upgrade` only when IsOS has an installed or indexed release whose signed/verified manifest, exact asset digest, core role, reader sets, required features and package contributions were checked against this graph. The field is either `null` or `{id,version,sha256}` for one exact release; no semver range, Git branch, URL guess or newer product version is sufficient. Listing a candidate never installs, selects or applies it. Without such verified evidence the action is to restore a compatible selected build or inspect the owner's release catalog. A future mismatch and an unknown version remain failures even if a proposed upgrade exists.

The P05 fixture set under [`tests/fixtures/reader_features/`](../../../tests/fixtures/reader_features/) freezes positive, negative and no-stop cases for the implementation and cross-repository replay. The companion EOS/EGIA contracts must be reviewed before this target becomes implemented.
