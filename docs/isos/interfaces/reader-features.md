# P05 reader and feature preflight

[中文](../../../docs_cn/isos/interfaces/reader-features_cn.md)

**Target design — not implemented.** IsOS owns admission of the saved deployment graph, exact package pins and selected core executables before Apply, Run or Restart. EOS and EGIA own the capability identities emitted by their binaries. This contract extends the [version overview](configuration.md#version-admission) and the schema-1 [local API](local-api.md#configured-builds-and-version-readiness); P05 work is tracked in the [0.x roadmap](../maintenance/roadmap.md). Reader compatibility does not itself establish runtime readiness: an enabled EGIA core still needs the EOS gateway health barrier.

## Caller, source of truth and probe

The operator calls `isos version check --json` or the owner-only loopback Graph Validate/Apply and deployment Run/Restart operations. IsOS reads the exact saved graph bytes and revision. For Validate it checks the submitted draft without writing; for Apply it repeats checks under the graph lock immediately before P04 publication; for Run/Restart it checks the saved revision, selected P04 generation and every intended child before stopping or spawning one. Migration preview checks the proposed `0.1.0` graph but never treats a read-only legacy projection as saved bytes. All probes are bounded and start no core runtime.

IsOS resolves the configured `aether-profile` setup reader, the EOS runtime, bridge and config-server from the actual IsOS process specifications, and the selected EGIA setup and runtime when EGIA is enabled. It probes the same executable bytes that P04 inventories and later launches. Capability probes exit within 5 seconds, emit at most 64 KiB of JSON stdout and never expose raw stderr in a public diagnostic. For EGIA, `bin/egia` is a shell launcher: `EGIA_PYTHON`/`ISLAND_PYTHON`, its `.venv` fallback, `ISLAND_PREFIX`, effective module search path and installed EGIA module code can change the Python process without changing the launcher file. P05 extends the P04 generation inventory with the resolved absolute interpreter and digest, effective nonsecret interpreter/module binding and verified installed EGIA code tree; probe and spawn use that same resolved chain, including an explicit resolved interpreter selection, and recheck it before active replacement. A missing interpreter fails without `uv sync`, virtualenv creation, package installation or other bootstrap. A path-only match, an unselected sibling build, a PATH lookup, a product-version comparison or a probe of a different binary cannot admit the child. A changed executable, interpreter, module tree, binding or package receipt between probe, P04 generation verification and spawn invalidates the preflight; Run/Restart fail before active child replacement. The EOS bridge and EGIA runtime do not read the graph, so their required runtime features are checked without demanding graph/type arrays.

Each enabled owner setup `identity` keeps schema-1 `core`, `product_version`, `setup_schema_version`, legacy `graph_version` and `node_type_version`, and advertises `supported_graph_versions`, `supported_node_type_versions`, `supported_node_types` and `features`. The arrays contain exact accepted versions and built-in type IDs; `features` contains stable ASCII feature IDs. Verified package contributions are checked in addition to, never impersonated by, built-in `supported_node_types`. The legacy scalars are aliases for older readers and do not override present arrays. EOS graph-reading children report `binary`, `product_version`, the supported arrays and `features` through bounded `--capabilities` probes; the EOS bridge reports only its existing identity and transport features. EGIA P05 adds a bounded, no-start, no-bootstrap `egia --capabilities` probe on its selected launcher; its runtime reports `binary`, `product_version` and `features` only, because it reads P04 managed configuration rather than the graph. Its setup adapter owns the graph/type arrays and exact four historical IDs. The P05 implementation verifies setup and runtime claims independently. A partially present, malformed, empty, duplicated or contradictory version/type array set fails closed. An older setup identity with all version/type arrays absent may use validated scalars as singleton sets only for an actual safe `1.0.0` graph, exact registered `@v1.*` types and an empty derived P05 setup-reader required-feature set; it cannot authorize `0.1.0`, `@v0.1` or a feature absent from an explicit `features` list. This setup fallback never bypasses an enabled runtime child's feature probe. An array that is present but omits a value never falls back to the scalar.

| Field | JSON type / unit | Purpose, absence and validation |
| --- | --- | --- |
| `supported_graph_versions` | nonempty array of unique strings / — | Exact graph wire versions read by that binary; missing permits only the legacy scalar fallback above. |
| `supported_node_type_versions` | nonempty array of unique strings / — | Exact registered type suffix versions, such as `0.1` and `1.0`; this is necessary but never sufficient to admit a type ID. |
| `supported_node_types` | array of unique full type IDs / — | Exact built-in IDs implemented by this reader. Missing permits only exact types in the frozen safe legacy registry; a contributed type also needs its verified package pin and owner catalog. |
| `features` | array of unique ASCII strings / — | Implemented capabilities of that binary. Missing means the empty set; a required feature then fails. |
| `binary` | stable executable ID string / — | Required for a runtime `--capabilities` reply and must equal the selected role, for example `aether-runtime`; setup identity uses `core` instead. |
| `product_version` | nonempty string / — | Reported release for display and provenance; it is not a reader compatibility predicate. |
| `setup_schema_version` | integer / — | Must equal `1` on setup identity; independent of graph and product versions. |

An EOS setup fixture reply is `{"schema_version":1,"ok":true,"diagnostics":[],"files":[],"identity":{"core":"eos","product_version":"fixture","graph_version":"1.0.0","node_type_version":"1.0","supported_graph_versions":["1.0.0","0.1.0"],"supported_node_type_versions":["1.0","0.1"],"supported_node_types":["eos.hardware.camera@v0.1"],"features":["setup-v1","graph-0.1-reader","catalog"],"setup_schema_version":1}}`. Exact EOS features and all built-in IDs for real binaries are fixed by the EOS companion contract. EGIA's current setup advertises both graph versions but only type version `1.0`, so that alone never admits an EGIA `@v0.1` type. A focused runtime fixture is `{"binary":"aether-runtime","product_version":"fixture","graph_version":"1.0.0","node_type_version":"1.0","supported_graph_versions":["1.0.0","0.1.0"],"supported_node_type_versions":["1.0","0.1"],"supported_node_types":["eos.hardware.camera@v0.1"],"features":["graph-0.1-reader","log-dir"]}`.

## Required set and admission order

IsOS parses the actual graph version and every enabled node's full registered type ID at its JSON Pointer. It first validates graph structure and safe legacy identity, then verifies each exact package receipt, contribution and pin before consuming its type catalog. An unknown future graph retains G01 `unsupported_graph_version`, and an unregistered or unmapped type retains its G01/G03 exact-path diagnostic; P05 `reader_graph_unsupported` and `reader_type_unsupported` apply only to known graph versions and registered types missing from the selected reader set. For EOS, IsOS first probes `--capabilities` without any sidecar or graph input, so the reply describes built-in capability only. It passes each verified sidecar as the existing repeatable `--node-types <absolute-path>` argument to the exact selected `aether-profile` setup/catalog/validation calls and actual EOS launch; `setup catalog` without those flags contains only built-ins. It checks contributed IDs against that combined catalog and the exact verified pin separately from the static capabilities reply. It derives required graph/type versions and feature IDs from the combined registered owner catalog, node configuration, edges and process role; graph-authored unknown feature strings do not grant capabilities. A suffix match cannot admit an unregistered type or a package-contributed type from a different pin. The MuJoCo process type is contributed by the verified `island/mujoco-sim@0.1.1` package; generic EOS camera, base and manipulator types are built in. Required features are checked against the exact binary that implements them. IsOS checks each enabled setup reader, each graph-reading runtime child, then non-reader transport children, and finally P04 rendered inputs, secrets and readiness prerequisites. Diagnostics are deterministic: saved graph path order, then binary role, then feature ID; a graph-wide feature points to `/version`. The first failure blocks Apply/Run/Restart. Package tamper retains its P01/P02 code and wins before reader mismatch. P04 generated snapshot mismatch wins before an attempted replacement; P05 never repairs it implicitly.

For the `0.1.0` EOS graph, `aether-profile`, `aether-runtime` and enabled `aether-config-server` each need `graph-0.1-reader`, `node-types` and `data-idl`. `aether-profile` also needs `setup-v1` and `catalog`; `aether-runtime` additionally needs the features selected by enabled nodes: `log-dir` when IsOS passes `--log-dir`, `primitive-binding` for a primitive node, `vision-gate` for a camera gate, and `mujoco-child-v2` for an admitted `eos.process.mujoco@v0.1` or `@v1.0` launch. EOS also requires this token for its legacy `eos.process.backend@v1.0` v2 child path, but IsOS G01/G03 rejects that authored legacy node before P05 as `migration_required`, so it creates no P05 runtime feature case. The existing fixed `short-paths` EOS process check remains. `aether-http-bridge` needs its declared `vision-ws` transport feature whenever its process is enabled, without a graph reader claim. EGIA setup needs `setup-v1`, `catalog`, `graph-0.1-reader`, the exact four registered legacy IDs and their graph/type sets for a `0.1.0` envelope. The selected EGIA runtime needs `managed-config-v1` and `eos-gateway-client-v2` for either accepted graph envelope, without graph/type arrays. These attest managed launch and client behavior, not EOS gateway readiness or future EGIA stages. A reader advertising `0.1.0` but not the requested exact registered type or required feature is incompatible.

## Typed failure and version report

The schema-1 HTTP envelope keeps `ok:false`, `error` and `data.diagnostics`; CLI emits the same stable code and a sanitized repair message, and `isos version check --json` includes the same diagnostic objects with each core's existing `ready`, `reason` and `action` fields. A P05 diagnostic contains exactly `code`, `path`, `message`, `stage` and `reader`. `reader` has `core`, `binary`, `binary_sha256` (lowercase 64-hex or `null` if the selected input cannot be read; for EGIA it hashes the canonical resolved launcher/interpreter/binding/module inventory, not the wrapper alone), `requested` and `supported`. `requested` contains only applicable `graph_version`, full `node_type`, `feature` and exact `{id,version}` package pin; absent values are `null`. `supported` contains sorted unique `graph_versions`, `node_type_versions`, full `node_types` and `features`; unknown sets are empty arrays. A graph-wide requirement points to `/version`; a node or package requirement points to its exact `/node_type` or `/package`, with JSON Pointer escaping. A missing runtime feature points to the requiring process or device `/node_type`. A selected child binary or launch-chain failure points to its authored IsOS process node `/settings/role` when present, otherwise that node's `/node_type`; the command path is synthesized rather than authored. A setup reader failure uses `""`. `stage` is `graph`, `package`, `reader` or `feature`. Stable codes are `reader_identity_invalid`, `reader_graph_unsupported`, `reader_type_unsupported`, `reader_feature_unsupported`, `reader_binary_mismatch`, and `reader_package_pin_mismatch`. `message` names the selected binary and an action, but never raw stderr, secrets, local paths or speculative releases.

For example, a graph reader lacking a required feature returns HTTP `422` with `data` containing `{"diagnostics":[{"code":"reader_feature_unsupported","path":"/cores/eos/layers/interface/groups/gate/nodes/preview/node_type","message":"aether-runtime lacks vision-gate; select a verified compatible build and Apply again","stage":"feature","reader":{"core":"eos","binary":"aether-runtime","binary_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","requested":{"graph_version":"0.1.0","node_type":"eos.interface.camera_gate@v0.1","feature":"vision-gate","package":null},"supported":{"graph_versions":["0.1.0","1.0.0"],"node_type_versions":["0.1","1.0"],"node_types":["eos.interface.camera_gate@v0.1"],"features":["log-dir"]}}}]}` and `error:"reader preflight failed"`. An unreadable or wrong selected executable reports its actual role and `reader_binary_mismatch` before spawn. A malformed identity reports `reader_identity_invalid`, with empty supported sets if the reply cannot be trusted.

`isos version check --json` may include `compatible_upgrade` only when IsOS has an installed or indexed release whose signed/verified manifest, exact asset digest, core role, reader sets, required features and package contributions were checked against this graph. The field is either `null` or `{id,version,sha256}` for one exact release; no semver range, Git branch, URL guess or newer product version is sufficient. Listing a candidate never installs, selects or applies it. Without such verified evidence the action is to restore a compatible selected build or inspect the owner's release catalog. A future mismatch and an unknown version remain failures even if a proposed upgrade exists.

The P05 fixture set under [`tests/fixtures/reader_features/`](../../../tests/fixtures/reader_features/) freezes positive, negative and no-stop cases for the implementation and cross-repository replay. The companion EOS/EGIA contracts must be reviewed before this target becomes implemented.
