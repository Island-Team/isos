# R06 dependent deployment stop contract

[中文](../../../docs_cn/isos/interfaces/dependent-stop_cn.md) · [Design](../design/dependent-stop.md) · [First use](../usage/get-started.md#r06-dependent-stop-target) · [Frozen cases](../../../tests/fixtures/dependent_stop/README.md) · [R06 task](../../../../Island-eos/docs/island/implementation-todo.md)

**Target design — not implemented.** IsOS owns the lifecycle of its direct EOS, EGIA, bridge and config child process groups, the response to its owner-only manager and loopback API callers, and the durable unknown stop intent. EOS owns Dispatcher stop admission, physical base and arm stop, and its direct MuJoCo child. MuJoCo owns the physical simulator acknowledgment. IsOS does not send actuator commands, adopt the simulator, or infer a safe stop from a disappeared PID.

## Caller, boundary and outcome

The same-UID CLI uses the existing schema-1 manager socket operation `deployment_stop`; the loopback workbench calls `POST /api/isos/v1/process-control` with `operation:"stop"`. Attached `isos run` Ctrl+C, `restart`, failed startup rollback, provider-loss recovery and `manager_shutdown` use the same supervisor stop primitive. An optional `revision` on the HTTP request has the existing stale-editor semantics. No graph, package or API setting can lengthen the R06 stop deadline. This adds no saved-graph field and does not change the schema-1 envelope.

```json
{"schema_version":1,"operation":"stop","revision":"7a8daee6b7db9105f5483506ffc1743625b63089710dfbf936622329c471016b"}
```

A completed stop returns the existing `stopped` array in reverse dependency order and an additive `terminal` object. `stopped` means that the named direct child was reaped; it is not a physical-stop assertion. A repeated stop returns an empty `stopped` array and the retained last terminal outcome for the last admitted run. On a home that has never run, `terminal` is null. A newly admitted Run/Restart begins with `terminal:null` for its new run until a stop is attempted; a preflight rejection before replacement keeps the old run and result.

```json
{"schema_version":1,"ok":true,"data":{"stopped":["egia","bridge","config","eos"],"terminal":{"run_id":"r42","outcome":"confirmed","reason_code":null,"processes":[{"id":"egia","outcome":"confirmed","reason_code":null},{"id":"bridge","outcome":"confirmed","reason_code":null},{"id":"config","outcome":"confirmed","reason_code":null},{"id":"eos","outcome":"confirmed","reason_code":null}]}} ,"error":null}
```

`outcome:"confirmed"` means every selected direct-child process group has exited and been reaped within the deadline and, for EOS, its R06 owner shutdown proof has succeeded. Any missing proof, timeout, signal failure, unexpected child exit, forced KILL, unconfirmed EOS physical stop, retained descendant or grant retirement failure yields `outcome:"unknown"`; it never becomes confirmed because the process is gone. `reason_code` is null only for confirmed and otherwise one of `child_exit_unexpected`, `stop_signal_failed`, `stop_deadline_exceeded`, `stop_forced_kill`, `stop_group_unreaped`, `eos_stop_unconfirmed`, `eos_receipt_missing`, `eos_receipt_invalid`, `eos_receipt_late`, `control_grant_retire_failed`, `stop_result_persist_failed`, or `stop_interrupted`. The overall outcome is unknown if any child outcome is unknown. A partial result still lists every selected child with one terminal outcome. Unknown is a completed manager request with `ok:true` and nonzero CLI exit status; callers must read `terminal.outcome`, not the HTTP status, to decide safety. Transport or owner authentication failures keep the existing `ok:false` error envelope.

For each admitted run, IsOS creates a private `data/stops/<deployment>/<run_id>.json` record beneath `0700` directories as a `0600` regular file with no symlink traversal. Its exact fields are `schema_version:1` (unsigned integer), `deployment` (validated slug, 1–48 ASCII letters, digits, `_` or `-`), `run_id` (exact P07 deployment run ID), `phase` (`running` or `stopping`), `outcome` (null for running, `unknown` for stopping), and `selected_processes` (bounded array of unique registered process IDs in planned reverse dependency order). The file never contains `confirmed` or a `terminal` phase. Unknown keys, missing fields, mismatched run/deployment, unsafe metadata or invalid transitions fail closed. The run-specific path prevents a late write from an earlier run overwriting a newer run. P07's durable last-run ID selects the record; this is not another graph or log stream.

After P07 durably publishes a new run and before first child spawn, IsOS atomically creates that run's `phase:running,outcome:null` file and fsyncs file and parent. If the two publications disagree after a crash, the P07 run recovers unknown and launch stays blocked; an unknown old run cannot be replaced without owner-reviewed safe recovery. Before normal graceful signaling, IsOS atomically replaces the same run file with `phase:stopping,outcome:unknown` and fsyncs file and parent. This fsync is the **single durable safety commit point for Stop**. A manager crash, missing file or uncertain intent write recovers unknown. A bounded intent-write worker may finish late, but it can write only `unknown` to that run's file; the stop owner does not wait past its budget before sending emergency signals. This is the sole exception to the durable-before-signal rule and always yields unknown, even if physical cleanup later succeeds. The in-memory terminal result may become `confirmed` only through the live finalization fence below. IsOS never writes durable confirmed, so a stalled rename or parent fsync cannot later upgrade a caller's unknown result. A clean live confirmation deliberately degrades to unknown after manager restart; operator recovery must use the reviewed EOS fence rather than a historical event.

## Stop deadline and EOS proof

The IsOS budget uses one monotonic `deployment.stop_timeout_ms` deadline, an unsigned integer of milliseconds with default **30,000** and valid range **5,000..120,000** in `config/isos.toml` only. `deployment.eos_stop_grace_ms` is an unsigned integer of milliseconds with default **20,000**, valid from **1,000** through `stop_timeout_ms - 3,000`, and reserves EOS time after dependents stop. Non-EOS dependent groups share no more than `min(8,000, stop_timeout_ms - eos_stop_grace_ms - 2,000)` milliseconds of graceful TERM. The overall deadline starts when stop closes admission; `cleanup_at = deadline - 2,000 ms`. At `cleanup_at` **at the latest**, IsOS ends graceful waits, sends SIGKILL to any still-live identity-safe owned group, marks forced targets unknown, and starts nonblocking reap polling. It spends at most 1,500 ms of the final window on kill/reap, leaving at least 500 ms for the live finalization fence and response. No filesystem call is on that finalization path. The stop owner and deadline timer serialize on one in-memory run-scoped fence. While holding it, the owner checks the monotonic clock and all child and EOS proofs, then atomically selects a terminal value and publishes that same value to the shared status and bounded nonblocking response queue. Confirmed publication must complete strictly before the deadline; if the queue cannot accept it then, the owner publishes unknown instead. At or after the deadline the timer publishes unknown; equality belongs to unknown. This logical publication precedes any later OS transport flush, which cannot change the queued result. Once published, the cell is immutable for that manager lifetime, including for a second caller; no background worker may alter it. An event may only describe the published value. A child not reaped by the finalization point remains unknown and is tracked for later best-effort cleanup without another signal to an unpinned group. An absent config field takes its default. Malformed, overflowing or invalid combinations fail with `stop_budget_invalid`, `stage:"config"` and `path:"/deployment/stop_timeout_ms"` or `"/deployment/eos_stop_grace_ms"` during manager validation and before a new launch. Each admitted run retains its validated budget, so a later malformed config cannot block emergency Stop. These are owner settings, never graph fields. EOS's approved 15,000 ms bound fits the default 20,000 ms grace within the 30,000 ms outer bound; a configured grace shorter than EOS's actual shutdown cannot accept a late receipt as confirmation.

Group signaling is identity safe only while IsOS retains the spawned direct-child leader **unreaped**. Linux `waitid(..., WNOWAIT)` observes its exit without releasing its PID; readiness and provider-loss polling must not call a reaping `try_wait` before the last group signal. The unreaped leader keeps its PID/PGID allocated, preventing reuse of the negative PGID. IsOS verifies the original `/proc/<pid>/stat` start ticks, process group and session against the held leader at spawn and before each `kill(-pgid, signal)`; inability to read or match them is ambiguous. Only after no later group signal is possible does it reap the leader. A pidfd identifies the leader but does not pin a PGID after reap. `EPERM`, an unexpected identity, an already reaped leader, or uncertain group membership fails closed as `stop_group_unreaped`: IsOS does **not** signal a possibly reused PGID and cannot report confirmed. After manager crash, a saved PID/PGID is never used for signaling because the unreaped-leader hold is gone; recovery reports unknown. Direct-child exit alone does not prove descendants left the group.

The approved [EOS R06 owner contract](https://github.com/Island-Team/Island-eos/blob/refactor%28v2%29/runtime-main/docs/eos/interfaces/simulator-stop.md) requires one `eos_terminal_stop` receipt from the selected EOS child's **raw stdout pipe**. IsOS consumes that pipe with a dedicated strict parser before P06 log normalization and passes the parsed result through a bounded channel. It never accepts a P06 stderr JSONL event, `eos_stopped` line, exit code alone, another process's pipe or a historical receipt as proof. IsOS checks `managed-stop-v1` during selected EOS build preflight only as a support announcement; the token never confirms a run. EOS closes or redirects the selected stdout writer in its MuJoCo child and helpers, so a descendant cannot hold EOF open. IsOS bounds line assembly and requires EOF after the one line and EOS exit to exclude a second receipt; a descendant-held writer or absent EOF by EOS grace is invalid and cannot delay the outer deadline.

The receipt is exactly one newline-terminated JSON object of at most **4096 UTF-8 bytes including newline**, with unique keys and no unknown or missing fields. `schema_version` is integer `1`; `type` is `eos_terminal_stop`; `run_id` and `active_revision` equal the admitted P07 run and applied SHA-256 revision; `eos_pid` equals the selected unreaped EOS leader PID. `backend_node` equals the selected canonical short path such as `eos/process/mujoco/sim`, never a `/cores/...` pointer. `backend_pid` and `backend_pgid` are positive unsigned IDs with `backend_pgid == backend_pid` for the separately sessioned MuJoCo child, or both null only for an unknown rollback before spawn. `generation_id` is lowercase 32-hex or null only if no child was ready and outcome is unknown. `stop_epoch` is a canonical ASCII decimal string or null without a valid stop response; confirmed requires it, while EOS owns comparison against its captured earlier epoch. `admission_closed`, `backend_group_drained`, `backend_reaped` and `sockets_removed` are booleans. `parts` contains exactly the selected stop-capable MuJoCo base and manipulator graph paths in canonical order, at most 64, each once, with unique paths and kinds, and only `node_path`, `kind` (`base` or `arm`) and `outcome` (`stopped` or `unknown`). An absent kind may be omitted only if no actuator of that kind was selected; EOS's whole-robot stop still proves both kinds. `outcome` is `confirmed` or `unknown`; `reason_code` is null exactly for confirmed, otherwise one of EOS's fixed `stop_timeout`, `stop_socket_unavailable`, `stop_response_invalid`, `stop_part_unknown`, `backend_exited`, `backend_forced_kill`, `backend_group_unreaped`, `backend_reap_failed`, or `socket_cleanup_failed`. No raw path, error or secret is accepted.

For IsOS `confirmed`, the one valid receipt must arrive from the selected pipe before the EOS grace and global deadline, declare `confirmed`, list every selected part `stopped`, and set all four fact booleans true. The observed EOS process must then exit **zero**, its identity-safe direct-child group must drain, and IsOS must reap the held leader before its own live finalization fence publishes confirmed. EOS's `backend_group_drained` covers every MuJoCo process-group member, beyond leader reap; IsOS checks its type and truth but cannot independently observe that nested group and relies on EOS owner proof. A receipt with the wrong run ID on the selected EOS pipe maps to `eos_receipt_invalid`, as do duplicate/unknown/missing JSON keys, malformed/oversized/partial lines, second receipts, missing EOF, mismatched PID/revision/backend/parts and inconsistent confirmed facts. Bytes on another process pipe or P06 stderr are never admitted to the selected EOS parser; if the selected pipe has no receipt, the result is `eos_receipt_missing`. A receipt at or after EOS grace but strictly before the global deadline maps to `eos_receipt_late`; an explicit EOS unknown receipt or nonzero EOS exit maps to `eos_stop_unconfirmed`. At or after the global deadline, while the terminal cell is still pending, `stop_deadline_exceeded` wins before receipt parsing or EOS-grace classification. A terminal value already published before that deadline remains immutable. This check occurs under the same run-scoped finalization fence, so timer and receipt arrival cannot race to choose different reasons. These all make the deployment terminal unknown even if a log or PID disappearance suggests success. EOS's hard phases close ingress by t0+1 s, classify physical stop by +4 s, reap its child by +10 s, publish receipt by +13 s and exit by +15 s from its first shutdown transition; IsOS does not extend any phase.

The stop order is reverse **dependency** order, with deterministic reverse launch order for independent peers. EGIA and other EOS consumers stop before the EOS provider. EOS is the final graph child, allowing its own bounded physical stop while its MuJoCo child remains alive. The bridge and config groups are stopped according to their declared dependencies; the manager never sends MuJoCo a direct signal. A second stop request while a stop is in progress joins the same operation and receives its result. Start or Restart cannot overlap a stop on the same deployment.

## Status, events and errors

`GET /api/isos/v1/process-status` adds `terminal` with the same shape. Its existing `state` remains live truth: an unknown stop is `degraded` with `last_error` set to a fixed safe explanation even when `processes` is empty; a confirmed stop is `stopped`. A failed Restart or rollback cannot publish `deployment_ready` until the old generation's stop is confirmed in the same live manager, unless the owner explicitly implements a fenced recovery that the EOS R06 contract proves safe. After manager restart, the previous run is unknown even if a former client saw confirmed, so it needs that owner-reviewed recovery before another launch. No automatic replay of an uncertain movement is allowed. A preflight failure leaves the old run, PID set, grants and current-run scope unchanged.

IsOS emits `deployment_stopping` once for an admitted run and exactly one terminal event, all with the same run ID and one request correlation ID. A normal confirmed Stop ends in `deployment_stopped`; a failed candidate start whose partial children stop cleanly ends in the existing `deployment_failed`; any unknown stop ends in `deployment_stop_unconfirmed`. Each terminal event has fixed sanitized `fields:{"outcome":"confirmed"|"unknown","reason_code":null|<listed code>}`. `deployment_stop_unconfirmed` has `level:error` and does not replace the P07 pinned first ready/failure anchor. `deployment_stopped` has `level:info`. The event is queued only after child reaping and the live finalization fence; a log write failure increments the existing counter and cannot delay stop. EOS emits its own stop events under `source:eos`; IsOS never forges them. A manager-session preflight rejection retains `deployment_preflight_failed` and does not emit `deployment_stopping` for the old run.

```json
{"schema_version":1,"ok":true,"data":{"stopped":["egia","eos"],"terminal":{"run_id":"r42","outcome":"unknown","reason_code":"eos_stop_unconfirmed","processes":[{"id":"egia","outcome":"confirmed","reason_code":null},{"id":"eos","outcome":"unknown","reason_code":"eos_stop_unconfirmed"}]}},"error":null}
```

The [fixture inventory](../../../tests/fixtures/dependent_stop/README.md) fixes the stop, timeout, provider-loss, rollback and log-outage paths. The R06 implementation must test real EOS and MuJoCo together as well as stub process groups; a fake `eos_stopped` event by an unselected child cannot become proof. No performance or physical safety claim follows from a stub alone.
