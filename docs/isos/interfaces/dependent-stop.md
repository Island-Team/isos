# R06 dependent deployment stop contract

[中文](../../../docs_cn/isos/interfaces/dependent-stop_cn.md) · [Design](../design/dependent-stop.md) · [First use](../usage/get-started.md#r06-dependent-stop-target) · [Frozen cases](../../../tests/fixtures/dependent_stop/README.md) · [R06 task](../../../../Island-eos/docs/island/implementation-todo.md)

**Target design — not implemented.** IsOS owns the lifecycle of its direct EOS, EGIA, bridge and config child process groups, the response to its owner-only manager and loopback API callers, and the durable deployment terminal state. EOS owns Dispatcher stop admission, physical base and arm stop, and its direct MuJoCo child. MuJoCo owns the physical simulator acknowledgment. IsOS does not send actuator commands, adopt the simulator, or infer a safe stop from a disappeared PID.

## Caller, boundary and outcome

The same-UID CLI uses the existing schema-1 manager socket operation `deployment_stop`; the loopback workbench calls `POST /api/isos/v1/process-control` with `operation:"stop"`. Attached `isos run` Ctrl+C, `restart`, failed startup rollback, provider-loss recovery and `manager_shutdown` use the same supervisor stop primitive. An optional `revision` on the HTTP request has the existing stale-editor semantics. No graph, package or API setting can lengthen the R06 stop deadline. This adds no saved-graph field and does not change the schema-1 envelope.

```json
{"schema_version":1,"operation":"stop","revision":"7a8daee6b7db9105f5483506ffc1743625b63089710dfbf936622329c471016b"}
```

A completed stop returns the existing `stopped` array in reverse dependency order and an additive `terminal` object. `stopped` means that the named direct child was reaped; it is not a physical-stop assertion. A repeated stop returns an empty `stopped` array and the retained last terminal outcome for the last admitted run. On a home that has never run, `terminal` is null. A newly admitted Run/Restart begins with `terminal:null` for its new run until a stop is attempted; a preflight rejection before replacement keeps the old run and result.

```json
{"schema_version":1,"ok":true,"data":{"stopped":["egia","bridge","config","eos"],"terminal":{"run_id":"r42","outcome":"confirmed","reason_code":null,"processes":[{"id":"egia","outcome":"confirmed","reason_code":null},{"id":"bridge","outcome":"confirmed","reason_code":null},{"id":"config","outcome":"confirmed","reason_code":null},{"id":"eos","outcome":"confirmed","reason_code":null}]}} ,"error":null}
```

`outcome:"confirmed"` means every selected direct-child process group has exited and been reaped within the deadline and, for EOS, its R06 owner shutdown proof has succeeded. Any missing proof, timeout, signal failure, unexpected child exit, forced KILL, unconfirmed EOS physical stop, retained descendant or grant retirement failure yields `outcome:"unknown"`; it never becomes confirmed because the process is gone. `reason_code` is null only for confirmed and otherwise one of `child_exit_unexpected`, `stop_signal_failed`, `stop_deadline_exceeded`, `stop_forced_kill`, `stop_group_unreaped`, `eos_stop_unconfirmed`, `eos_receipt_missing`, `control_grant_retire_failed`, `stop_result_persist_failed`, or `stop_interrupted`. The overall outcome is unknown if any child outcome is unknown. A partial result still lists every selected child with one terminal outcome. Unknown is a completed manager request with `ok:true` and nonzero CLI exit status; callers must read `terminal.outcome`, not the HTTP status, to decide safety. Transport or owner authentication failures keep the existing `ok:false` error envelope.

| Field | Type / unit | Purpose, default, validation and compatibility |
| --- | --- | --- |
| `terminal` | object or null / — | Additive stop result in process-control, owner manager reply and `GET /process-status`. Null before any admitted run and while a newly admitted run has not begun stopping; retained after Stop, failure and manager restart. A corrupted or unreadable terminal record is reported as unknown with `stop_result_persist_failed`, never reconstructed as confirmed. |
| `terminal.run_id` | ASCII deployment run ID / — | Exact last admitted `r...` ID from P07, 1–64 letters, digits, `_` or `-`; never a manager-session ID or a caller-supplied ID. |
| `terminal.outcome` | `confirmed` or `unknown` / — | All-child stop proof; no implicit default. Older clients may ignore the additive object but must not treat `stopped` as proof of physical safety. |
| `terminal.reason_code` | listed code or null / — | Fixed first safety-relevant failure in stop order; null exactly for confirmed. No raw OS error or path. |
| `terminal.processes` | array of objects / records | One entry per selected direct child in reverse dependency order, maximum the admitted process count. No simulator child entry: EOS owns MuJoCo. A child that had already exited has unknown outcome unless its owner proof was previously captured. |
| `terminal.processes[].id` | registered process ID / — | Exact selected IsOS process ID, 1–48 ASCII letters, digits, `_` or `-`, never a PID. |
| `terminal.processes[].outcome` | `confirmed` or `unknown` / — | Direct child group and owner proof; no default. |
| `terminal.processes[].reason_code` | listed code or null / — | Fixed reason; null exactly for confirmed. |

IsOS stores one private `data/stops/<deployment>.json` state record beneath a `0700` directory as a `0600` regular file, with no symlink traversal. Its fields are `schema_version:1` (unsigned integer), `deployment` (validated deployment slug, 1–48 ASCII letters, digits, `_` or `-`), `run_id` (exact P07 deployment run ID), `phase` (`running`, `stopping`, or `terminal`), `outcome` (null while running, `unknown` for stopping, and `confirmed` or `unknown` for terminal), and `reason_code` (null or a listed fixed reason). `selected_processes` is a bounded array of unique registered process IDs in planned reverse dependency order, written before first spawn and retained through stopping so crash recovery can report each selected child. The bounded terminal `processes` outcome array appears only for `phase:terminal`. Unknown keys, missing fields, mismatched run/deployment, unsafe metadata, or invalid transitions cannot be interpreted as confirmation. IsOS atomically replaces the whole file, fsyncs file and parent, and never updates another run in place. P07's durable last-run identity remains the source of correlation; this is not another graph or log stream.

Before sending a stop signal, IsOS durably replaces `phase:running` with `phase:stopping,outcome:unknown` for the same run. A manager crash or uncertain write during this transition recovers as unknown. On manager restart, a last-run `phase:running` record is also unknown because IsOS cannot reattach an old direct-child supervision hold; only a durable confirmed terminal record survives as confirmed. A newly admitted run atomically resets the record to its new `run_id,phase:running,outcome:null` after P07 publishes that run and before first child spawn; an unknown old run cannot be replaced without owner-reviewed safe recovery. If P07 and stop state disagree after a crash between those writes, the new run is unknown and launch remains blocked. A failed intent write must not leave moving hardware unattended: IsOS still sends bounded emergency stop signals, marks the in-memory result unknown and relies on P07's durable run ID plus any nonterminal stop state to recover unknown. It cannot emit a confirmed result. A confirmed terminal response requires an atomic, fsynced `phase:terminal,outcome:confirmed` write; failed or late persistence keeps the durable intent unknown and reports `stop_result_persist_failed`. A recovered unfinished `phase:stopping` reports `stop_interrupted`.

## Stop deadline and EOS proof

The proposed IsOS budget uses one monotonic `deployment.stop_timeout_ms` deadline, an unsigned integer of milliseconds with default **30,000** and valid range **5,000..120,000** in `config/isos.toml` only. The proposed `deployment.eos_stop_grace_ms` is an unsigned integer of milliseconds with default **20,000**, valid from **1,000** through `stop_timeout_ms - 3,000`, and reserves EOS time after dependents stop. Non-EOS dependent groups share no more than `min(8,000, stop_timeout_ms - eos_stop_grace_ms - 2,000)` milliseconds of graceful TERM. The overall deadline starts when stop closes admission; `cleanup_at = deadline - 2,000 ms`. At `cleanup_at` **at the latest**, IsOS ends graceful waits, sends SIGKILL to any still-live identity-safe owned group, marks forced targets unknown, and starts nonblocking reap polling. It spends at most 1,500 ms of the final window on kill/reap, leaving at least 500 ms for terminal-state publication. A child not reaped by then remains unknown and is tracked for later best-effort cleanup without another signal to an unpinned group. A final-state worker may prepare and fsync a temporary file, but can rename it to confirmed only after checking the live deadline under the stop-state lock; if fsync finishes late, it discards the temporary file and leaves the durable unknown intent. The caller does not wait past the deadline for that worker, collector, or child. An absent config field takes its default. Malformed, overflowing or invalid combinations fail with `stop_budget_invalid`, `stage:"config"` and `path:"/deployment/stop_timeout_ms"` or `"/deployment/eos_stop_grace_ms"` during manager validation and before a new launch. Each admitted run retains its validated budget, so a later malformed config cannot block its emergency Stop. These are owner settings, never graph fields. **The EOS graceful-stop bound and reservation formula remain proposals pending EOS owner agreement.**

Group signaling is identity safe only while IsOS retains the spawned direct-child leader **unreaped**. Linux `waitid(..., WNOWAIT)` observes its exit without releasing its PID; readiness and provider-loss polling must not call a reaping `try_wait` before the last group signal. The unreaped leader keeps its PID/PGID allocated, preventing reuse of the negative PGID. IsOS verifies the original `/proc/<pid>/stat` start ticks, process group and session against the held leader at spawn and before each `kill(-pgid, signal)`; inability to read or match them is ambiguous. Only after no later group signal is possible does it reap the leader. A pidfd identifies the leader but does not pin a PGID after reap. `EPERM`, an unexpected identity, an already reaped leader, or uncertain group membership fails closed as `stop_group_unreaped`: IsOS does **not** signal a possibly reused PGID and cannot report confirmed. After manager crash, a saved PID/PGID is never used for signaling because the unreaped-leader hold is gone; recovery reports unknown. Direct-child exit alone does not prove descendants left the group.

EOS R06 needs a **machine-checkable owner terminal outcome** tied to the exact run ID and observed EOS PID, proving that Dispatcher admission closed, required base and arm stops were acknowledged or positively fenced, the MuJoCo child was reaped, and owned sockets were cleaned up. A process exit code or `eos_stopped` line alone does not prove dual physical acknowledgment. The proposed transport is a bounded structured EOS terminal receipt admitted from the selected child pipe and cross-checked against exit status and child identity; the exact event code, fields, signal semantics and maximum EOS bound are **pending EOS owner agreement** in R06 design review. Until that reviewed contract exists, IsOS must classify EOS as `unknown` with `eos_receipt_missing`; any EOS explicit unknown outcome or nonzero exit is `eos_stop_unconfirmed`. IsOS never upgrades an unknown result based solely on a generic log line or a child PID disappearing.

The stop order is reverse **dependency** order, with deterministic reverse launch order for independent peers. EGIA and other EOS consumers stop before the EOS provider. EOS is the final graph child, allowing its own bounded physical stop while its MuJoCo child remains alive. The bridge and config groups are stopped according to their declared dependencies; the manager never sends MuJoCo a direct signal. A second stop request while a stop is in progress joins the same operation and receives its result. Start or Restart cannot overlap a stop on the same deployment.

## Status, events and errors

`GET /api/isos/v1/process-status` adds `terminal` with the same shape. Its existing `state` remains live truth: an unknown stop is `degraded` with `last_error` set to a fixed safe explanation even when `processes` is empty; a confirmed stop is `stopped`. A failed Restart or rollback cannot publish `deployment_ready` until the old generation's stop is confirmed, unless the owner explicitly implements a fenced recovery that the EOS R06 contract proves safe. No automatic replay of an uncertain movement is allowed. A preflight failure leaves the old run, PID set, grants and current-run scope unchanged.

IsOS emits `deployment_stopping` once for an admitted run and exactly one terminal event, all with the same run ID and one request correlation ID. A normal confirmed Stop ends in `deployment_stopped`; a failed candidate start whose partial children stop cleanly ends in the existing `deployment_failed`; any unknown stop ends in `deployment_stop_unconfirmed`. Each terminal event has fixed sanitized `fields:{"outcome":"confirmed"|"unknown","reason_code":null|<listed code>}`. `deployment_stop_unconfirmed` has `level:error` and does not replace the P07 pinned first ready/failure anchor. `deployment_stopped` has `level:info`. The event is appended after child reaping and terminal-state publication; a log write failure increments the existing counter and cannot delay stop. EOS emits its own stop events under `source:eos`; IsOS never forges them. A manager-session preflight rejection retains `deployment_preflight_failed` and does not emit `deployment_stopping` for the old run.

```json
{"schema_version":1,"ok":true,"data":{"stopped":["egia","eos"],"terminal":{"run_id":"r42","outcome":"unknown","reason_code":"eos_stop_unconfirmed","processes":[{"id":"egia","outcome":"confirmed","reason_code":null},{"id":"eos","outcome":"unknown","reason_code":"eos_stop_unconfirmed"}]}},"error":null}
```

The [fixture inventory](../../../tests/fixtures/dependent_stop/README.md) fixes the stop, timeout, provider-loss, rollback and log-outage paths. The R06 implementation must test real EOS and MuJoCo together as well as stub process groups; a fake `eos_stopped` event by an unselected child cannot become proof. No performance or physical safety claim follows from a stub alone.
