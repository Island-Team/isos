# IsOS configuration, version, and log contract

[中文](../../../docs_cn/isos/interfaces/configuration_cn.md)

**Status:** The XDG/`ISOS_HOME` roots, `config/isos.toml`, schema-1 local API, rotating source logs, and `isos version check` exist. The P04 generated configuration and launch preflight below are implemented in IsOS. Full P05 reader-set admission and cross-core event fields remain **0.x targets**; some owner binaries already advertise supported-version arrays. See [current API fields](local-api.md#local-runtime-configuration) and [first-use workflow](../usage/get-started.md).

## Paths and precedence

`ISOS_HOME` must be absolute. When set, `<base>/config`, `<base>/data`, and `<base>/run` are the three roots. Otherwise IsOS uses `${XDG_CONFIG_HOME:-~/.config}/isos`, `${XDG_DATA_HOME:-~/.local/share}/isos`, and `${XDG_RUNTIME_DIR:-/run/user/<uid>}/isos`. IsOS owns these paths, uses owner-only directories (`0700`) and private files (`0600`), and never treats the command working directory as configuration.

| Relative path and owner | Kind / purpose | Write and validation rule |
| --- | --- | --- |
| `config/deployments/<name>.nodes.json` / IsOS | Authored deployment graph | `name` is a validated slug; revision is SHA-256 of saved bytes; only revision-checked Apply or explicit migration writes it. |
| `config/services/<id>.toml` / IsOS | Independently started model-like service | Explicit service command only; never a graph node in this release. |
| `config/mode` / IsOS | `dev` or `product` mode | `isos init` writes; invalid values fail startup. |
| `data/generated/<name>/v2/<revision>/<generation>/` / IsOS | P04 validated core setup snapshot | **Target:** immutable leaf selected by a revision-checked `data/generated/<name>/selection.json`; see the exact contract below. Existing `data/generated/<name>/<revision>/` and flat legacy snapshots remain readable without mutation. |
| `data/packages/<namespace>/<name>/<version>/` / IsOS | Verified exact package release, receipt, node-type sidecar | Installation or link creates a receipt; never activates a graph. Linked source changes are re-fingerprinted at Apply and Run. |
| `data/logs/<name>/` / IsOS and EOS child | Rotating JSONL source files and unified `events.log` | Owner-only; cursor reads bounded; an active run ID appears in target events. |
| `data/cache/` / IsOS | Download and catalog cache | **Target:** disposable; identity comes from verified receipt and digest, not cache presence. |
| `run/manager.sock`, `run/<name>-*.sock` / owning process | Private manager and core sockets | UID checked; remove stale sockets only after owner identity check. |

`ISOS_CONFIG` points to an absolute TOML file when set; otherwise IsOS reads its checkout `config/isos.toml`. For each supported TOML field, an explicitly set environment variable wins, then TOML, then the documented default. Relative source-artifact paths in TOML resolve from the IsOS checkout. `ISOS_HOME`/XDG select private state roots independently. Never store secrets in graph settings, generated snapshots, receipts, logs, or UI preferences. Service `env_from` imports a named process environment variable at launch; status prints the name, never its value. A missing required secret fails preflight without echoing it.

## P04 generated configuration and launch preflight (implemented in IsOS)

IsOS owns the saved-byte revision, generation selection, private files and child launch. EOS and EGIA own the contents returned by their schema-1 `setup render` adapters; IsOS never edits an owner overlay. Apply is the only writer. Validate may render into memory but publishes nothing. Run and Restart consume only the selected generation and never silently refresh it. P05 separately negotiates the actual reader feature and version sets.

| Field or path | Type / unit | Purpose and validation |
| --- | --- | --- |
| `revision` | 64 lowercase hexadecimal characters / SHA-256 | Digest of the exact saved graph bytes, not parsed JSON; required in the selection and manifest. |
| `generation` | 64 lowercase hexadecimal characters / SHA-256 | Digest of canonical, lexicographically sorted input inventory: revision, selected core binary paths and hashes, verified package `{id,version,receipt_sha256}` entries, selected EGIA component/factory default source paths and file hashes, and final rendered file paths and hashes. No clock, PID, secret value or implicit working-directory search enters the inventory. |
| `selection.json` | JSON object / — | Schema `2` revision-indexed map: `{"schema_version":2,"entries":{"<revision>":{"kind":"v2","generation":"<sha256>"}}}`. An entry may instead be `{"kind":"g03"}` only for an explicitly recorded, unmarked pre-P04 G03 revision. Keys are exact saved-byte SHA-256 values. Preserve prior entries needed by the current or active revision when replacing the whole private `0600` file atomically. The saved graph digest selects its own entry; a different revision's entry never selects a leaf for it. |
| `v2/required/<revision>.json` | immutable JSON marker / — | `{"schema_version":1,"revision":"<sha256>"}` is published with private `0600` permissions and parent fsync for every successfully P04-applied `0.1.0` revision. It is separate from `selection.json` and never removed by re-Apply. If this marker exists, a missing, malformed, `g03`, or invalid v2 selection fails Run/Restart; the G03 revision-only snapshot cannot be used. If a valid v2 selection is present but its marker is absent after an interrupted first Apply, recovery verifies the leaf and finishes the marker under the graph lock before Run. Only an unmarked revision with no v2 entry may use the verified G03 path. |
| `manifest.json` | JSON object / — | Schema `2` with `revision`, `generation`, sorted `files`, `launch_inputs`, `packages`, `default_roots`, `defaults`, and `secret_refs`. Each file entry has relative POSIX `path` and lowercase `sha256`; launch inputs have `core`, `binary`, absolute `path` and `sha256`; packages have exact `id`, `version`, and `receipt_sha256`; `default_roots` is `null` when EGIA is disabled or has absolute `component` and `factory` paths when enabled; defaults have `source` (`component` or `factory`), relative `path`, and `sha256`, and are empty when EGIA is disabled. `secret_refs` is a sorted array of `{node_path,env_from}` entries and is empty when none are declared. Reject duplicate, unknown, traversal or symlinked paths and fields. `files` enumerates every leaf file except `manifest.json`; no unlisted file is accepted. The manifest and every listed regular file are `0600` beneath a `0700` leaf. |
| `eos/graph.json` | JSON bytes / — | Required EOS owner render. Its hash and exact bytes must match a fresh render before Run/Restart. EOS's effective `--profile` points here; the authored graph remains in `config/`. |
| `egia/` | TOML bytes / — | Required when the EGIA process is enabled. Seed the complete selected installed EGIA `etc/egia` default tree, then replace exactly `egia/egia.toml`, `egia/modes.toml`, and `egia/profiles/isos.toml` with EGIA's validated render. Required effective files are `egia.toml`, `modes.toml`, `profiles/isos.toml`, `models.toml`, `prompts.toml`, `missions.toml`, `safety/gate.toml`, and `opt/sandbox.toml`; copy other declared regular defaults as well. Reject missing required files, symlinks, special files, collisions, escaping references and unsupported source layouts. No unlisted factory fallback may supply a missing value at launch. |
| `secret_refs` | array of node path and child-to-manager environment-name map / — | Deployment entries derive only from target component `settings.env_from`; existing independent-service `env_from` follows the same spawn rule outside this manifest. Both names match `[A-Za-z_][A-Za-z0-9_]*`. The manifest records names only. Before stopping any active child, resolve and validate every required value for **all** intended children into a private, short-lived launch plan; reject a missing or empty value without printing it. At spawn, pass each value only to its named child, then discard that child's copy. Do not serialize values in the graph, manifest, logs, status, or diagnostics. Raw graph `settings.env` is never interpreted as a secret-reference mechanism. |

The installed EGIA default trees are explicit `paths.egia_defaults_dir` and `paths.egia_factory_defaults_dir` inputs from the configured EGIA distribution, not a working-directory discovery. Both are required when EGIA is enabled; IsOS must confirm that the factory path equals the root the selected EGIA launcher will actually use. IsOS checks the selected `egia-config` and `egia` binaries and every default file as regular files without following symlinks, records their SHA-256 digests, and rejects a source that changes between render and publication. The component defaults are copied into the leaf; the factory defaults remain an inventoried launch input and must be checked again before Run/Restart and spawn. An unlisted factory fallback is a preflight failure. P01's verifier supplies only exact pinned package handles; a package sidecar or unverified directory cannot become a core default. The EOS profile and EGIA configuration are both derived from one saved graph revision and one verified pin set. `EGIA_ETC` and the explicit `--etc` argument both name the absolute `egia/` directory in the selected leaf; `--mode isos --managed --no-tui` remains the managed launch form. No implicit source-checkout file may supply a missing effective value.

For the generation digest, take the complete manifest object except its `generation` member, encode it as compact UTF-8 JSON with object keys sorted lexicographically, no insignificant whitespace and no trailing newline, then SHA-256 those bytes. Sort `files` by `path`, `launch_inputs` by `(core,binary)`, `packages` by `(id,version)`, `defaults` by `(source,path)`, and `secret_refs` by `node_path` before encoding; sort each `env_from` map by child name. Paths use their selected absolute spelling for roots and binaries and normalized relative POSIX spelling for files. A verifier recomputes this digest; a syntactically valid manifest with a wrong generation is rejected.

Apply rechecks the expected saved-byte revision, package handles, binary/default digests and owner renders under the final graph lock. It stages and fsyncs an immutable leaf, then atomically publishes that absent leaf and fsyncs its parent. Next it builds a complete schema-2 selection map retaining the old current and active entries (including an explicit `g03` entry for an unmarked G03 snapshot) and adding/replacing the candidate revision's v2 generation. It writes a temporary map, fsyncs it, renames it to `selection.json`, and fsyncs the selection parent. For a first P04 Apply of that revision it writes the marker to a private temporary file, fsyncs it, atomically renames it to `v2/required/<revision>.json`, and fsyncs that parent; an existing marker is never rewritten. A same-revision v2 re-Apply ends at the selection-map rename and parent fsync: the marker already exists, and graph bytes do not change. A first same-revision upgrade from G03 completes only after the marker is durable. For a changed or first graph, the marker and map must be durable **before** the staged graph file is atomically renamed and its parent fsynced. The graph rename is the saved-byte publication point. Apply never changes active children; a new generation for unchanged bytes requires explicit Apply and leaves the old leaf immutable.

Before selection-map rename, failure leaves the old saved graph and old map untouched. After selection-map rename, a changed graph still selects its retained old entry while a same-revision graph may select either complete old or new generation; no active child changes. A failed marker publication leaves the map observable: recovery completes a missing marker for a verified current-revision v2 entry before Run, and a future-revision entry remains inert while the old graph is saved. Before graph rename, the old saved graph remains; after graph rename, only the observed old or new complete state is allowed. A post-rename/pre-parent-fsync failure at the selection, marker, or graph boundary returns `generated_commit_uncertain` at `stage:"publish"`, never a claim that the old state is intact. Recovery under the graph lock rereads the exact graph bytes, selection map, marker and complete selected leaf. If the graph still has the old revision, it uses that revision's retained entry and leaves a future entry inert; if it has the new revision, the new marker and v2 entry must validate before Run/Restart. A valid v2 map entry without a marker from an interrupted first same-revision upgrade is finished by publishing the marker; otherwise recovery fails closed. Re-fsync the relevant parent after an uncertain rename and resolve the result by the observed saved-byte revision and generation. A map missing after a successful P04 Apply cannot cause a G03 fallback because the independent marker remains. Unused leaves and map entries may be collected only after no saved or active revision references them.

Run and Restart reread saved bytes, the matching selection entry and the independent marker under the deployment lock, verify P01 exact package handles and the complete manifest/file set, recompute the generation inventory from current installed inputs, and compare a fresh owner render byte-for-byte. A changed file plus a changed manifest hash still fails the owner-render comparison. They resolve **all** required secret names for **every** intended child, including later dependency-ordered children, before any active child is stopped; a missing value reports the exact escaped `/cores/isos/layers/process/groups/component/nodes/<node>/settings/env_from/<target>` JSON Pointer with `generated_missing_secret` at `stage:"spawn"`. Values remain in the private launch plan and are passed only to the matching child at its spawn. All preflight checks finish before stopping or replacing an active child; a failure leaves its active state unchanged. A `1.0.0` saved graph retains its existing flat generated snapshot and safe legacy admission until explicit migration; P04 does not rewrite those graph bytes.

P04 failures use the existing schema-1 local API envelope with `422` for admission failure and `500` for `generated_commit_uncertain`, plus a bounded `data.diagnostics` array. Each diagnostic has exactly `code`, `path` (JSON Pointer or empty for a global input), `message`, and `stage`; messages name the repair action without local source paths, raw adapter stderr, TOML content, secret names or values. The stable codes are `generated_revision_mismatch`, `generated_missing_input`, `generated_unsafe_path`, `generated_invalid_default`, `generated_owner_rejected`, `generated_manifest_mismatch`, `generated_render_mismatch`, `generated_missing_secret`, and `generated_commit_uncertain`. Stages are `graph`, `package`, `binary`, `defaults`, `render`, `publish`, `snapshot`, or `spawn`. A node-specific failure points at its exact saved graph path; a global file failure uses `""`. For example, a missing EGIA prompt file is `{ "code":"generated_missing_input", "path":"", "message":"Restore the selected EGIA installation and Apply again", "stage":"defaults" }`. A missing or corrupt selection for a marked revision is `generated_manifest_mismatch` at `stage:"snapshot"`; a selection with no matching saved revision is `generated_revision_mismatch` at `stage:"graph"`. A missing child secret points to the exact `settings.env_from` target key, with JSON Pointer escaping applied to each node and key segment; the diagnostic message does not repeat the source name. CLI exits nonzero with the same code and sanitized message. A rejection before selection-map rename activates no candidate; later publication failures and uncertain outcomes are resolved from observed graph bytes, map, marker and leaf as described above.

## Version admission

| Identity | Target value or rule | Compatibility meaning |
| --- | --- | --- |
| Product releases | IsOS/EGIA/IsosUI `0.1.0`, EOS `0.2.0`, MuJoCo package `0.1.1` | No product is declared stable `1.0.0`. |
| Authored graph writer | `0.1.0` | Reader also accepts existing `1.0.0` saved graphs; original bytes stay unchanged. |
| New node type ID | `@v0.1` | Legacy `@v1.0`/`@v1.1` IDs retain their registered safe behavior. |
| HTTP API path and setup envelope | `/api/isos/v1`, `schema_version:1` | Stable compatibility identity; not product release number. |
| Package release manifest | `schema_version:4` | Distribution format; exact package version is separate. |
| MuJoCo socket protocol | `2.0.0` | Existing simulator wire identity; EOS and package must agree. |

**P05 target algorithm:** The [reader-feature contract](reader-features.md) defines the exact selected-binary probes, full type and verified package checks, required feature mapping, scalar fallback, typed diagnostics and upgrade evidence. Apply and Run repeat these checks against current graph bytes and executable digests. A changed package, graph or executable invalidates the selected P04 generation. Never reinterpret a `1.0.0` graph as `0.1.0` to pass a check. Current IsOS admission still uses narrower scalar and partial-array probes; P05 is not yet implemented.

## Target shared JSONL event

Each module logs one `info` event when it becomes ready, then state transitions, warnings and failures; periodic health produces a log only on change or a bounded summary interval. Full child output remains in its owner's log store. IsOS's unified stream receives bounded, sanitized events. Logging must not stall actuator stop or process shutdown.

| Field | JSON type / unit | Purpose, default, validation, compatibility |
| --- | --- | --- |
| `timestamp` | RFC 3339 UTC string / ms | Required event time; preserve existing field. |
| `level` | `trace`, `debug`, `info`, `warn`, `error` / — | Required severity; existing filter order stays. |
| `source` | string / source ID | Required 1–48 ASCII letters, digits, `_` or `-`; identifies emitter. |
| `core` | string / core ID | Required runtime owner (`isos`, `eos`, or `egia`); MuJoCo child events use `eos` with `source:mujoco`. |
| `node_path` | string or null / canonical path | Optional owner node; null or absent for a global event. |
| `event_code` | string / machine code | Required stable lowercase snake case, 1–64 characters; existing optional readers still accept it. |
| `run_id` | string / opaque ID | Required owner session identity; IsOS uses a manager-session ID before deployment starts and a deployment-run ID thereafter, and attaches one when normalizing legacy `log_append`. |
| `correlation_id` | string or null / opaque ID | Optional request correlation; no secret or user text embedded. |
| `message` | string / UTF-8 bytes | Required human explanation, max 8192 bytes, redacted before write. |
| `fields` | object / bounded metadata | Optional scalar values only, maximum 16 keys and 4 KiB encoded; deny secrets, paths with credentials, and unbounded payloads. |
| `pid` | integer or null / process ID | Optional existing process metadata. |

```json
{"timestamp":"2026-11-01T10:00:00.000Z","level":"info","source":"eos","core":"eos","node_path":null,"event_code":"runtime_ready","run_id":"r-7c2a","correlation_id":null,"message":"EOS runtime ready","fields":{"state":"ready"},"pid":4242}
```

Read with `isos logs all --level info` or `GET /api/isos/v1/logs?source=all&limit=100`; use `next_cursor` to poll. One read is limited to 200 lines or 64 KiB; `rotated:true` means the cursor file was replaced and the UI must show that gap. Existing defaults are 256 KiB per file, two backups, 32 source files, and `info` minimum. New source files beyond that cap still appear in the unified stream. Never infer readiness from the startup log alone: `isos status --json` is authoritative live state.

**Target ingestion algorithm:** validate source/level/length, attach the authenticated owner and run context, remove secret keys and credential-like values, bound fields, write one JSON line to source and unified streams, rotate under a lock, and return without blocking on a slow UI reader. A dropped or rejected event increments an observable counter; warning emission is rate-limited to avoid recursion. HTTP and CLI cursors apply display filtering after storage. Existing `log_append` remains a small owner-only compatibility entry point; future cross-core transport may add fields without requiring old callers to send them.
