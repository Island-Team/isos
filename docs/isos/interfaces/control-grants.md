# R03 managed EOS control grants

[中文](../../../docs_cn/isos/interfaces/control-grants_cn.md) · [Design](../design/control-grants.md) · [First use](../usage/get-started.md#r03-managed-control-grant-replay) · [Frozen cases](../../../tests/fixtures/control_grants/README.md)

**IsOS issuer implemented; cross-repository R03 qualification pending.** IsOS owns issuance and delivery for a managed deployment run. EOS owns verification, admission, the Dispatcher and durable results. The [EOS gRPC contract](https://github.com/Island-Team/Island-eos/blob/refactor%28v2%29/runtime-main/docs/eos/interfaces/grpc.md#r03-governed-actuator-admission-target-contract) defines request metadata and operation semantics. No graph wire, package, generated overlay, browser request or client-supplied stage claim grants actuator authority. The local OS user is the trust boundary; this contract does not authenticate one same-UID process against another.

## Inputs, files and recipients

IsOS accepts the exact saved `0.1.0` graph revision and an **explicit selected P04 schema-2 V2 generation** only after package, reader, owner render, binary and secret preflight. The selected EOS runtime must advertise the exact P05 `managed-control-grants` feature; an older binary fails before any active child stops or a grant is issued. The saved-byte SHA-256 is `active_revision`; the EOS projection digest is a separate identity. IsOS verifies the selection entry, `data/generated/<deployment>/v2/<revision>/<generation>/manifest.json` and its single listed regular `eos/graph.json` before issuing grants. A missing selection or G03 fallback, even for a `0.1.0` graph, cannot issue grants or stop an active child. Legacy `1.0.0` and G03 snapshots never receive a control-grant bundle. Validate, Apply and migration do not issue grants.

For each new deployment `run_id`, IsOS draws **two independent 32-byte random values** from the operating-system CSPRNG. It creates `run/control-grants/<deployment>/<run_id>/` beneath its private runtime root, with owner-only `0700` directories, no symlink component and no existing destination. Each regular grant file is `0600`, contains exactly 64 lowercase hexadecimal characters followed by one newline, and decodes to 32 bytes. The verifier is a distinct `0600` regular JSON file with no grant bytes:

```json
{
  "schema_version": 1,
  "run_id": "<exact deployment run ID>",
  "active_revision": "<64 lowercase hexadecimal saved-byte SHA-256>",
  "egia_control_sha256": "<SHA-256 of decoded EGIA grant bytes>",
  "operator_control_sha256": "<SHA-256 of decoded operator grant bytes>"
}
```

The bundle paths are `egia-control.grant`, `operator-control.grant` and `verifier.json` in that run directory. IsOS writes each new file without following links or replacing an existing file, fsyncs the files and directory before use, and checks owner UID, regular-file type, mode and exact content on reuse. A collision, short random read, unsafe path, malformed file or verifier mismatch fails closed before EOS actuator-write readiness. Status and diagnostics may report the run ID, revision and a stable sanitized error code; they never report a grant, digest of a grant, file contents or bearer metadata.

| Recipient and channel | Private launch input | Authority delivered |
| --- | --- | --- |
| Managed EOS runtime | `EOS_CONTROL_GRANTS_FILE=<absolute verifier.json>` | Verifier digests and exact run/revision only; no plaintext grant. |
| Supervised EGIA child | `EGIA_EOS_CONTROL_GRANT_FILE=<absolute egia-control.grant>` | EGIA role grant; the managed client sends it as bearer metadata to governed EOS gRPC methods. |
| Supervised EOS HTTP bridge | `AETHER_BRIDGE_CONTROL_GRANT_FILE=<absolute operator-control.grant>` | Operator role grant for the bridge's owner-side control path and allowed governed stop/estop calls. It never enters HTML, JavaScript, browser payloads or public HTTP responses. |

The manager injects these variables into only the named **selected** child at spawn, overriding any authored `settings.env` entry of the same name and removing inherited values from other children. A managed `0.1.0` actuator deployment requires both selected `eos` runtime and `config` process specs for the existing P04 generated-profile projection. The `config` child receives no grant. The `egia` and `bridge` process specs are optional: their absence neither blocks a valid EOS-plus-config launch nor causes IsOS to pass their grant path to another child. A selected recipient means a verified process spec with the matching ID and role (`eos`/`eos`, `egia`/`egia`, or `bridge`/`eos`). IsOS checks the complete candidate spec set and recipient mapping before removing or stopping an active deployment; omission of required EOS or of a declared selected recipient fails preflight. An injection failure after `deployment_starting` terminates that candidate run and may require a distinct recovery run. An author cannot choose the path or role via `env_from`, `args` or a graph setting. EOS admits `egia-control` for governed gRPC movement, but no private browser route; it admits `operator-control` for bridge `primitive_typed` movement and governed gRPC stop/recovery, but rejects operator gRPC movement. Both roles may invoke authenticated `safety.estop` and query, watch or cancel only their own durable operations. The bridge sends `authority_grant` as an outer owner-socket field; the browser cannot supply it. EOS verifies role and method at admission. Possession of a per-run secret proves its issued role within the same-UID boundary, not an EGIA safety-stage claim; EGIA's fixed stage route is an A02 gate.

## Run lifecycle and observable failures

Run/Restart finish the existing P04/P05 preflight and resolve all `env_from` values before replacing an active child. They also reject authored `--run-id`/`--run-id=...` and other owner-injected flags (`--backend-release-sha256`, `--backend-payload-sha256`, `--log-dir`) in selected EOS runtime/bridge/config `settings.args` before stop; the existing generated-profile check rejects a duplicate `--profile`. IsOS prepares the candidate bundle before stop, but makes it available only to the candidate children. An idempotent Start retains the current `run_id`, revision and bundle. An automatic EOS, EGIA or bridge child restart within the same deployment run reuses the same bundle so a lost operation reply can be queried by the same ID. Explicit Restart creates a new run ID and grants even when the saved revision is unchanged. A failed replacement is terminal for its candidate run; if IsOS restores the old specifications, that recovery is another new run ID and bundle. The old bundle is retired after its children are reaped; a rejected preflight leaves old children and bundle unchanged. Stop reaps children before retiring its bundle. A manager restart creates a new deployment run rather than silently reviving an old grant.

EOS enters managed admission only with **both** the selected IsOS `v2/<revision>/<generation>/eos/graph.json` profile path and `EOS_CONTROL_GRANTS_FILE`; either alone fails startup before listener bind. Neither means standalone read-only, even if `--run-id` is present. In managed admission, EOS compares the verifier's exact `run_id` to its effective IsOS-supplied `--run-id` argument and its `active_revision` to the admitted schema-2 manifest revision before public write readiness. It validates its selected profile against the manifest entry and bytes independently. A missing, stale, unsafe or mismatched bundle prevents actuator write readiness and must not produce an EOS ready claim for writable capabilities. IsOS treats a child that only bound a socket as unready. Existing schema-1 manager and HTTP envelopes remain unchanged. A grant rejection **before** `deployment_starting` emits sanitized `deployment_preflight_failed` under the manager-session ID and request correlation; it leaves an older active deployment and P07 current-run scope unchanged. A failure **after** `deployment_starting` belongs to the candidate deployment run and ends in its terminal failure event. The saved graph bytes do not change in either case; active revision changes only after a successful replacement or distinct recovery run.

The following codes are proposed for the IsOS launch boundary: `control_grant_unsafe_path`, `control_grant_invalid_file`, `control_grant_mismatch`, `control_grant_issue_failed` and `control_grant_delivery_failed`. Each reports `stage:"spawn"` and an empty graph `path`, since the files are runtime state rather than authored fields. `control_grant_unsafe_path` covers ownership, mode, symlink and nonregular-file failures; `control_grant_invalid_file` covers shape or length; `control_grant_mismatch` covers run/revision/digest mismatch; `control_grant_issue_failed` covers random generation or durable publication; `control_grant_delivery_failed` covers candidate-plan omission of required EOS or a declared selected EGIA/bridge recipient detected before stop, or actual injection failure after candidate start. The latter cannot promise unchanged old PIDs; it terminates the candidate run and starts distinct recovery if possible. An absent optional EGIA or bridge spec is not an error. Authored owner-reserved flags instead return `control_grant_reserved_arg` at `stage:"graph"` with the exact `/cores/isos/layers/process/groups/component/nodes/<id>/settings/args/<index>` pointer; `--run-id=...` points to its own array element. The P04 generated-profile check keeps ownership of duplicate `--profile` admission. CLI exits nonzero, while API uses its existing error envelope. The error text is a repair action and never contains grant bytes or file content. Runtime operation authorization errors remain EOS gRPC status codes, not IsOS graph diagnostics.
