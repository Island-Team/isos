# Shared node graph and IsOS process nodes

[中文](../../../docs_cn/isos/interfaces/node-graph_cn.md)

Find each IsOS-owned kind by `core → layer → group → node` in the [node catalog](../layers/README.md). This page remains the authority for serialized fields, validation and compatibility.

**Implementation status:** New graphs, the `0.1.0` writer, the exact `@v0.1` built-in catalog, and explicit saved-graph migration are implemented. Safe `1.0.0` and `@v1.*` graphs remain readable by exact identity. Full G06 edge admission is implemented. Product versions, graph versions, node type IDs, HTTP paths, and simulator socket protocol are independent.

A saved graph at `~/.config/isos/deployments/<name>.nodes.json` (or `ISOS_HOME/config/deployments/`) configures IsOS and EOS, and may declare EGIA nodes. New graphs use `0.1.0`; legacy `1.0.0` graphs retain their saved bytes until explicit migration. A node type declares its core, layer, group, fields, and ports; an instance supplies its ID and settings. For `0.1.0`, IsOS validates its process nodes and whole-graph placement, then calls each enabled owner setup adapter for scoped validation and rendering. The graph SHA-256 is the saved revision; an active process set retains its revision until restart.

`isos init` writes a `0.1.0` editable graph only when absent and exits. The new draft contains EOS process nodes and the dispatcher; preview an installed package node set to add hardware. `isos config validate <file>` checks the package and graph; `isos config apply <file> --revision <saved-sha256>` applies a saved `0.1.0` draft, using `--revision ""` when the destination graph is absent. `isos serve` runs the owner-only manager and UI. `isos run` and `restart` stay attached; `isos deployment stop` stops only this graph, while `isos stop` shuts down the manager and all owned children. EOS starts MuJoCo before admitting hardware operations and stops it with the EOS runtime. A package install or link never changes an active deployment.

## Backend node

New package-contributed MuJoCo process nodes use `eos.process.mujoco@v1.0` at `eos/process/mujoco/<id>`. Their exact package is `profile.package:{id,version}`; settings contain `scene`, `socket`, optional `env`, and `start_timeout_ms` with the types and limits below. Camera, base, and manipulator devices use generic EOS types at `eos/hardware/camera/<id>`, `eos/hardware/base/<id>`, and `eos/hardware/manipulator/<id>`. Each device selects a package-pinned adapter family in `profile.adapter`; the package does not own the generic hardware node type.

| Setting | Rust type | Unit | Purpose and validation |
| --- | --- | --- | --- |
| `scene` | `String` | scene ID | Required ID from the descriptor; selects one XML scene. |
| `socket` | `PathBuf` | Unix path | Required owner-only socket under IsOS runtime, absolute and at most 107 bytes. EOS adapters must use this path. |
| `env` | `BTreeMap<String,String>` | environment | Optional runtime values passed only to the simulator child. `MUJOCO_ROOT` locates the library; `MUJOCO_GUI=1` requests the simulator's visible window on a graphical host. Keys are ASCII alphanumeric or `_`, values exclude NUL. |
| `start_timeout_ms` | `u64` | ms | Readiness deadline, default 30000, range 1–120000. |

The backend descriptor's `entrypoint`, `scenes`, `devices`, `protocol`, and MuJoCo runtime requirement are verified at apply and run. IsOS checks referenced scene assets and includes their bytes in the link fingerprint. Each EOS hardware adapter must name the backend in `references`, set `adapter.settings.backend` to its canonical path, match `socket_path` to the backend socket, and match `device_id`/`simulator_node` to the package device for its camera/base/manipulator group.
IsOS passes the verified executable and scene as explicit EOS runtime arguments and the verified MuJoCo library path in the EOS child environment. EOS starts the simulator, scopes the backend `env` values to that child, and waits for the configured Unix socket.

## Component process node

Path: `cores/isos/layers/process/groups/component/nodes/<id>`. Current type: `isos.process.component@v1.1`; saved `@v1.0` nodes are rejected with conversion guidance.

| Setting | Rust type | Unit | Purpose and validation |
| --- | --- | --- | --- |
| `role` | `String` | core ID | Required `eos` or `egia` for managed `isos.process.component@v1.1` nodes; selects the configured core binary directory. |
| `args` | `Vec<String>` | argv arguments | Arguments for the binary determined by `role`, at most 63 bounded strings; no shell or executable path. |
| `command` | `Vec<String>` | argv | Obsolete; rejected on Apply. Use `role` and `args`. |
| `cwd` | `Option<PathBuf>` | path | Optional absolute working directory. |
| `env` | `BTreeMap<String,String>` | environment | Optional child variables; keys ASCII alphanumeric or `_`, values exclude NUL. |
| `ready_tcp` | `Option<String>` | host:port | TCP readiness probe; exclusive with `ready_unix`. |
| `ready_unix` | `Option<PathBuf>` | Unix path | Socket readiness probe, absolute and at most 107 bytes; exclusive with `ready_tcp`. |
| `start_timeout_ms` | `u64` | ms | Readiness deadline, default 30000, range 1–120000. |
| `restart` | `Restart` | policy | `never`, `on_failure`, or `always`. |
| `max_restarts` | `u32` | attempts | Automatic restart cap, maximum 10. |
| `depends_on` | `Vec<String>` | canonical node paths | Prerequisites; unique, existing, and acyclic. |

The manager starts direct children in dependency order, waits for readiness, and stops process groups in reverse order with TERM then KILL after two seconds. Provider failure stops dependents before recovery. IsOS diagnostics and selected structured child events are stored in rotating `$XDG_DATA_HOME/isos/logs/<deployment>/<source>.log` files; plain child output is not mirrored. Status includes saved/active revision, pinned package, process PID/restarts, and last supervisor error. The private Unix manager API retains its schema 1 envelope and uses `deployment_start`, `deployment_restart`, `deployment_stop`, and `deployment_status` operations.

## Current EOS control nodes and legacy skill compatibility

Existing `1.0.0` graphs may contain `manual_0`, `base_velocity_0`, `arm_joint_0`, and `demo_0` under `cores/eos/layers/control`. Their historical types are `eos.control.manual@v1.0`, `eos.control.primitive@v1.0`, and `eos.control.skill@v1.0`. `demo_0` and `eos.control.skill@v1.0` are **compatibility-only**: new `0.1.0` graphs do not author a graph skill sequence or workflow node. These nodes describe configured command sources; runtime requests and outcomes remain separate typed data. Each control references the canonical EOS dispatcher path. Manual and primitive nodes also reference their target hardware node; a skill references its primitive steps. These references do not create an actuator route: the existing dispatcher output remains the only hardware command input.

| Setting | Rust type | Unit | Purpose and validation |
| --- | --- | --- | --- |
| Manual `target` | `String` | canonical node path | Required base or manipulator target; must name an admitted hardware node and appear in `references`. |
| Primitive `target` | `String` | canonical node path | Required hardware target; must name an admitted base or manipulator node and appear in `references`. |
| Primitive `movement_type` | `String` enum | movement mode | Required `body_velocity` for base or `joint_positions` for manipulator; must be supported by the target. |
| Legacy skill `steps` (compatibility-only) | `Vec<String>` | ordered canonical node paths | Required ordered primitive references; each path must be present in `references` and resolve to a registered primitive node. |

Manual and primitive nodes require a `status: Status` input from the dispatcher and a typed observation input from their target: `base_observation: BaseObservation` or `manipulator_observation: ManipulatorObservation`. Skill nodes require `status: Status` from the dispatcher. Manual and primitive nodes expose `request: ControlRequest` and `outcome: CommandOutcome` outputs; skill nodes expose `outcome: SkillOutcome`. The node ID is the final type name plus an index by default; `manual_0` is a current example, while `demo_0` is a legacy compatibility example. It is a graph identity, not a movement payload.

See [backend package design](../design/backend.md) and [local API](local-api.md).

## Canonical node paths and primitive bindings


`eos.dispatcher.primitive_base@v1.0` and `eos.dispatcher.primitive_manipulator@v1.0` are binding nodes. Their `settings` identify `primitive_name`, `primitive_version`, and `movement_type` (strings). Hardware `inputs.command` is an array of `{node,output}` edges from bindings; each binding output must reach one compatible hardware node. The adapter implementation is selected on the hardware instance through `adapter.type`, independently of its generic hardware node type. The IsOS Vision profile is `isos.ui.vision@v1.0` under `isos/ui/panel`; it is an internal UI node, not a supervised process.

## Graph `0.1.0` writer and compatible reads — G03 and G06 implemented

Newly authored graphs write `version: "0.1.0"`; new type registrations use `@v0.1`. G03 implements the writer, exact legacy migration, and baseline core/type placement admission. G06 admits every edge and reference against the aggregate owner catalog. Existing saved `1.0.0` graphs and their registered `@v1.0`/`@v1.1` types remain readable for the safe behavior they already provide. There is no blanket conversion of type IDs: a legacy graph retains its exact IDs, and an unavailable type reports a path-specific migration diagnostic. In particular, the old arbitrary-command `isos.process.component@v1.0` is never executed. Its replacement is a role-selected `isos.process.component@v0.1` with `role` and bounded `args` as above. Historical wire routes, protobuf packages, release-manifest schema v4, and MuJoCo socket protocol `2.0.0` do not change.

| Graph field | JSON type / unit | Owner and purpose | Default and validation | Compatible extension |
| --- | --- | --- | --- | --- |
| `version` | string / graph format | IsOS selects parser and writer | Required `0.1.0` for new drafts; reader also accepts `1.0.0` | No implicit rewrite of saved legacy bytes |
| `robot.id`, `robot.name` | strings / — | Operator identity and display name | Required nonblank strings | Additive metadata only |
| `cores` | object keyed by core ID / — | IsOS graph root; each core owns its subtree | Required, registered keys; unknown core fails admission | New core requires registered owner |
| `layers`, `groups`, `nodes` | nested objects keyed by path segment / — | Core owns placement; type registry validates it | Registered segments; unique four-part `core/layer/group/node` path | New registered placements may be added |
| `node.id` | string / path segment | Instance identity; equals its `nodes` key | Required valid segment | Never silently rename |
| `node.node_type` | string / versioned ID | Registry selects behavior | Required registered ID at declared placement | Existing IDs retain meaning |
| `node.label`, `node.description` | strings / — | Operator-facing instance title and function | Required; description may be empty on legacy instances but new nodes require nonblank text | Existing descriptions preserved |
| `node.package`, `node.adapter.package` | `{id,version}` / exact package pin | IsOS resolves contributed type or adapter | Required for a contributed type or selected package adapter; ID is `namespace/name`, version numeric `x.y.z` | Pin changes require Apply |
| `node.settings` | object / type-specific | Node type owner declares settings; IsOS validates package selectors | Empty object when no settings; unknown settings rejected by type contract | Optional setting additions have defaults |
| `node.inputs` | object of port names to source or source array / — | Registry validates typed connections | Empty when no inputs; each source must resolve to an output with the exact same registered `data_type` ID, cardinality must match; schema `x-unit` annotations do not authorize conversion | Optional edge metadata below |
| `node.references` | string array / canonical paths | Owner declares non-data dependencies | Empty by default; paths exist, unique where type requires | Additive references must not create actuator routes |
| `node.adapter`, `capabilities`, `health_timing`, `observation`, `movement`, `frame_id`, `joint_names` | typed objects/arrays/strings / type-specific | EOS hardware profile fields | Follow the [EOS hardware interface](https://github.com/Island-Team/Island-eos) (`docs/eos/interfaces/hardware.md`); IsOS forwards without inventing hardware meaning | EOS defines compatible defaults |

The registered **type** has a separate, nonblank `description` for new `@v0.1` types. It explains function, inputs, outputs, and operator-visible effects. Old verified sidecars lacking this field receive a generated catalog-only fallback; IsOS and EOS never modify the sidecar bytes. A setting's optional `selector` is defined by the [EOS node contribution contract](https://github.com/Island-Team/Island-eos) (`docs/eos/interfaces/node-contributions.md`); IsOS owns the [resolved options response](local-api.md#release-target-setting-options--not-implemented).

Each `node.inputs.<port>` source adds optional scheduling metadata:

| Source field | JSON type / unit | Purpose | Default and validation | Compatibility |
| --- | --- | --- | --- | --- |
| `node` | string / canonical node path | Output owner | Required existing source node | Unchanged |
| `output` | string / port name | Output port | Required registered output compatible with destination data type | Unchanged |
| `priority` | integer / Linux nice scale | Weighted delivery order | 0; inclusive `-20..19`, lower number has higher priority | Absent legacy value normalizes to 0 |
| `frequency_hz` | number / Hz | Maximum delivered update rate on this edge | Absent means no edge cap; if present finite and `>0` | Absent legacy edge remains uncapped |

Example **source-object fragment** for a compatible input port (target JSON, not yet accepted by current binaries):

```json
{"node":"eos/hardware/camera/front","output":"frame","priority":5,"frequency_hz":15.0}
```

Place this object in a registered `eos.interface.camera_gate@v0.1` node's `inputs.frame` when its source is an `eos.hardware.camera@v0.1` node. Command bindings have no user QoS. The [current starter template](../../../templates/generic-graph.toml) shows a complete graph without target edge fields. The producer's `expected_rate_hz` is a registry hint, independent of this edge cap. R01 will use a monotonic token bucket per active eligible evidence edge and weighted fair delivery over bounded queues. Observation overflow must increment a visible counter and emit a rate-limited warning; a command that cannot be admitted must be explicitly rejected or reported uncertain, never silently dropped. Stopping a route discards non-command queued work and invokes dispatcher stop for actuators. Scheduling priority never changes command authorization: actuator data still passes the dispatcher. IsOS stores and validates edge metadata; it does not schedule hardware itself. IsosUI renders both values on a wire and identifies design-only edges that have no runtime route.

Reader algorithm: read at most 1 MiB and calculate the SHA-256 revision from the **original saved bytes**, before JSON decoding or normalization. Dispatch only exact graph versions `1.0.0` and `0.1.0`; validate each original node type ID against its exact registered identity and established safe behavior. This reader retains the original JSON value; existing owner validators apply their established optional-field defaults during typed projection. A separate shared normalized projection remains future work and cannot change saved bytes or type identities. Unknown versions remain inspectable as raw JSON in the workbench but cannot be validated, applied, rendered, run, or restarted; those operations fail at `/version` with the supported set. Invalid JSON cannot be displayed as a graph. See the [architecture algorithm](../design/system.md).

The compatibility reader preserves original saved bytes and their SHA-256. A safe saved `1.0.0` graph remains inspectable and, once applied, read-only until explicit migration; an unapplied legacy starter may still receive its first safe Apply. A revision-matched, structurally identical legacy Apply returns the original revision without writing, even when the submitted JSON formatting differs. A changed applied legacy graph returns `migration_required`. Explicit migration previews the deterministic old-to-new diff, requires the original saved revision, and writes `0.1.0` bytes only after owner validation and setup succeed. It preserves IDs, paths, references, edges, exact package pins, and fields accepted by the old schema; unmapped fields or types are rejected at exact paths. Arbitrary-command `isos.process.component@v1.0` and `settings.command` are never converted. The old `eos.process.backend@v1.0` requires an exact verified replacement. A failed parse, package check, setup render, or stale revision leaves saved bytes and the active revision unchanged; even successful migration changes the active revision only after Restart.

The fixed compatibility inputs in [`tests/fixtures/graph_compat/`](../../../tests/fixtures/graph_compat/README.md) include a safe `1.0.0` graph, an equivalent graph with different whitespace, a `2.0.0` future graph, an unknown type ID, and an unsafe command process. Their bytes and expected paths are test fixtures, not templates for a new deployment.

## G03 explicit graph migration

IsOS owns migration of a **saved** safe `1.0.0` graph. Preview and commit operate on that saved file, never on an editor-supplied replacement graph. A preview reads at most 1 MiB, hashes the original bytes, validates the exact parser, type IDs, package pins, settings, references, and edges, then constructs one deterministic `0.1.0` JSON value. It changes only `/version` and the exact type IDs listed below. Existing instance IDs, paths, descriptions, settings, references, edges, adapter metadata, and exact `{id,version}` pins remain byte-equivalent as JSON values. Optional defaults are projected for checking but are not inserted into the migrated value. The acceptance boundary is the generic graph fields, each registered node type and settings schema, and verified package contribution schemas; only explicitly declared extension maps retain their members. Other unknown fields cause `unmapped_graph_field` at their JSON Pointer instead of disappearing through typed deserialization. Canonical bytes use lexicographically ordered object keys, two-space indentation, UTF-8, and no trailing newline, matching default `serde_json::to_vec_pretty` on `serde_json::Value`. The proposed revision is SHA-256 of those exact bytes that commit would write, and the preview returns those bytes as a JSON value plus a bounded change list. More than 256 changes fails with `migration_change_limit` at `/changes`; the list is never truncated. Preview never edits saved bytes or generated configuration.

| Exact old type | Exact target type | Owner and precondition |
| --- | --- | --- |
| `eos.hardware.camera@v1.0` | `eos.hardware.camera@v0.1` | EOS generic camera type registered and settings/ports revalidated. |
| `eos.hardware.base@v1.0` | `eos.hardware.base@v0.1` | EOS generic base type registered and settings/ports revalidated. |
| `eos.hardware.manipulator@v1.0` | `eos.hardware.manipulator@v0.1` | EOS generic manipulator type registered and settings/ports revalidated. |
| `eos.dispatcher.control@v1.0` | `eos.dispatcher.control@v0.1` | EOS dispatcher type registered; command admission remains with Dispatcher. |
| `eos.dispatcher.primitive_base@v1.0` | `eos.dispatcher.primitive_base@v0.1` | EOS binding type registered; its target and command route revalidated. |
| `eos.dispatcher.primitive_manipulator@v1.0` | `eos.dispatcher.primitive_manipulator@v0.1` | EOS binding type registered; its target and command route revalidated. |
| `eos.interface.camera_gate@v1.0` | `eos.interface.camera_gate@v0.1` | EOS camera gate type registered; evidence edge revalidated. |
| `isos.process.component@v1.1` | `isos.process.component@v0.1` | IsOS role-selected process type registered; `role` and bounded `args` revalidated. IsOS owns this contribution; EOS must accept it through owner-scoped validation or an explicit IsOS contribution, not as an EOS built-in. |
| `eos.process.mujoco@v1.0` | `eos.process.mujoco@v0.1` | Only when the **same exact pinned verified package** contributes the new process type and its existing scene/socket settings validate. Until then the legacy node stays read-only with `unmapped_node_type`. |

Only the four EGIA historical design identities may retain their exact IDs in a `0.1.0` proposal, because EGIA's G05 reader explicitly admits them in that envelope: `egia.common.source@v1.0`, `egia.common.context@v1.0`, `egia.common.planner@v1.0`, and `egia.common.guard@v1.0`. They acquire no new runtime route; missing EGIA reader support still blocks migration at `/node_type`. The legacy EOS `eos.control.manual@v1.0`, `eos.control.primitive@v1.0`, and `eos.control.skill@v1.0` have no `@v0.1` replacements and cannot pass EOS's `0.1.0` type-version check. They remain read-only with `unmapped_node_type` at the exact node path and guidance to remove or author an available new binding. The same conservative rule applies to `isos.ui.vision@v1.0` and `isosui.system.vision@v1.0` until their owners explicitly register compatibility for the `0.1.0` envelope. `isos.process.component@v1.0` and any `settings.command` fail with `unsafe_process_node`; `eos.process.backend@v1.0`, package-specific `eos.hardware.mujoco_*@v1.0`, and unknown IDs have **no automatic mapping**. The latter need an operator-authored replacement with an exact verified package/adapter; changing a suffix alone is insufficient. No graph-authored skill sequence is created.

A preview can show `can_apply:false` and exact diagnostics while a mapped graph is waiting for owner readers. Commit requires the saved original-byte revision and the preview's proposed revision. Before publish, IsOS requires its own `0.1.0` registry and every enabled core's `setup identity` to advertise graph `0.1.0`; it checks **exact** type registrations, not just `supported_node_type_versions`, and runs each owner's `validate` and `render` on the proposed value. The current EOS profile still reports scalar graph `1.0.0`, and the current starter lacks an EOS-visible IsOS `component@v0.1` contribution. Both are concrete blockers until the EOS reader-features and IsOS registration slices land. EGIA's compatible graph envelope supports only its four historical common IDs, so new `@v0.1` EGIA stages remain blocked. A reported product version or graph envelope alone never grants type admission.

Under the graph lock, commit compares the supplied original revision with the current saved-byte SHA-256 and recomputes the proposal; a stale source or proposal returns a conflict without writes. It validates receipts, linked-package fingerprints, scene/assets, edge admission, and both core renders before staging. It fsyncs and publishes an immutable generated snapshot under the **proposed** revision first, then fsyncs a same-directory graph temporary file and atomically renames the graph last. Failure before graph rename leaves saved bytes and active revision unchanged; staged temporary files are removed and an unused published snapshot may be garbage-collected. No validation, setup, or launch follows graph rename, but IsOS still fsyncs the graph parent directory. If that fsync fails or a connection fails after rename, the result is `commit_outcome_uncertain`; the caller cannot assume old bytes remain and must reread the saved revision to determine whether commit succeeded. Even a successful migration changes only the **saved** revision; running children keep `active_revision` until explicit Restart, which revalidates the exact new graph and packages.

### G03 writer and snapshot selection

After owner-reader qualification, a **missing** deployment graph yields an editable `0.1.0` draft from GET; `isos init` and `isos config init` create the `0.1.0` starter only when the file is absent. They never rewrite an existing `1.0.0` graph. The new starter uses `eos.dispatcher.control@v0.1` and IsOS-owned `isos.process.component@v0.1` role-selected children. A first PUT on a missing graph requires `revision:""`; subsequent changed `0.1.0` PUTs require the exact saved revision. The CLI's changed `0.1.0` Apply requires `--revision <saved-sha256>` (or `--revision ""` for a missing graph). Both write canonical `0.1.0` bytes only after the same preflight and CAS as migration. A saved safe `1.0.0` graph remains inspectable; structurally identical Apply stays a no-op, an unapplied legacy starter may use its legacy first Apply, and changed applied legacy bytes require migration. New drafts do not silently downgrade to `1.0.0` because an owner reader is unavailable: Init may create an offline `0.1.0` draft, while Apply reports `owner_reader_unavailable` and leaves saved bytes unchanged.

For `0.1.0`, generated files live at `data/generated/<deployment>/<saved-revision>/`, containing `core-setup/launch-inputs.json`, `eos/graph.json`, and the enabled core overlays. The manifest records source revision, exact graph/package/executable digests, generated file paths and digests, and validates before Run or Restart. IsOS chooses this directory **only by the current saved graph's SHA-256** and verifies its manifest; there is no mutable `current` pointer or symlink. EOS runtime and config-server `--profile` arguments are replaced at launch with this directory's verified `eos/graph.json`; the saved graph's `settings.args` remain unchanged. The legacy `data/generated/<deployment>/core-setup/launch-inputs.json` layout remains a read-only compatibility input for `1.0.0` Run/Restart and applied-state GET; a `0.1.0` reader never falls back to it. `GET /node-graph` derives `read_only` from version/admission and legacy applied state, not from an unrelated snapshot directory. `GET /process-status` obtains `active_revision` from the manager's launched revision, not a generated path.

Run and Restart compare the stored generated bytes with a fresh owner render from the exact saved graph, so a file and manifest changed together cannot authorize a different projection. A rebuilt core binary invalidates the launch-input digest. `isos init` reports the stale input and does not mutate the immutable snapshot; restoring the pinned binary or creating a new graph revision and applying it is required before launch.

Before owner projection, IsOS rejects any `0.1.0` core key other than `eos`, `isos`, or `egia` at `/cores/<core>` with `unsupported_core`. It checks each node against the exact approved target identity set and registered `core/layer/group` placement, reporting `unsupported_node_type` or `invalid_node_placement` at the node's `/node_type`. Legacy IsOS/IsosUI Vision identities and unmapped EOS control identities are not admitted inside a new graph, even if the legacy catalog still lists them.

The `0.1.0` validation handshake is owner-scoped. IsOS parses and validates the complete graph, including exact node paths, references, package pins, and all cross-core links; its own registry validates `isos.process.component@v0.1` and other IsOS types. The IsOS aggregate catalog merges these own definitions with EOS and verified package contributions. For `0.1.0`, IsOS calls EOS setup Validate/Render on the full graph, and EOS projects and validates only the `eos` core; EGIA setup validates its own subtree. IsOS does **not** call the legacy whole-graph `aether-profile validate --file` for `0.1.0`, since that would incorrectly require EOS to own IsOS process types. Legacy `1.0.0` retains its existing whole-profile validation. Undeclared cross-core edges and references in a proposed `0.1.0` graph block migration, Apply, and Run at their exact paths, including those preserved from a legacy graph. The enabled owner adapters must advertise `0.1.0`, validate/render successfully, and the launched EOS runtime must accept the generated projection before IsOS publishes the graph.

## G06 graph-wide edge admission — implemented contract

For `0.1.0`, IsOS resolves every `inputs` source and `references` entry against the complete, version-admitted catalog before migration commit, Validate, Apply, Run, or Restart. It checks the source and target paths and registered placements, output and input names, exact data-type ID (including its one registered `x-unit` schema), cardinality and duplicate sources, declared transport, required inputs, and cycles. A missing or ambiguous type descriptor blocks admission; suffix or port-name similarity does not infer compatibility. A source object uses its actual JSON Pointer; a source array uses its numeric index. Diagnostics include that pointer, `source`, `target`, `input`, stable code, and the relevant declared type/unit when available. A reference is a dependency, never a data edge or command permission. IsOS checks process `depends_on` separately, including cycles and stop order.

In M1, this aggregate catalog contains EOS built-ins and historical EGIA common descriptors served by EOS, IsOS's role-selected component definition, and verified package contributions. EGIA does not yet publish a separate port catalog; its four common `@v1.0` descriptors support design inspection and are never treated as live routes.

Each admitted edge has one routing class. `eos_local` has two EOS-owned endpoints; `egia_local` belongs to EGIA; `service_bridge` requires an exact registered cross-core bridge pair and transport; all other admitted descriptive edges are `design_only`. The M1 owner route table contains exactly one routed candidate: `eos.hardware.camera@v0.1.frame` → `eos.interface.camera_gate@v0.1.frame`, data type `camera_frame`, `in_process` transport and image data class. IsOS matches both exact type IDs, ports, data type, transport and class; mere EOS placement or a similar catalog port does not imply routing. This table is versioned by its exact `@v0.1` endpoint IDs and changes only with reviewed owner-contract updates; missing route metadata means unrouted and QoS-ineligible. A route-table entry authorizes only declarative `routed:true` status; R01 will implement delivery. EOS's `FixedSafety` classification maps to public `route_class:eos_local`, `fixed:true`, `routed:false`, and `qos_eligible:false` for graph edges; the active Dispatcher command path remains a separate governed runtime route. EGIA-local edges remain `routed:false` until EGIA A04 publishes exact owner routes. No `service_bridge` is admitted in M1: the candidate camera-gate preview → Vision path lacks a registered `0.1.0` Vision destination and exact bridge declaration. It must fail until those exist. An undeclared cross-core edge is invalid even if data types match. A cross-core reference needs an owner-declared dependency or service purpose; it cannot establish an actuator route. IsOS returns class, `fixed`, `qos_eligible` and `routed` status to inspectors. `design_only` is always unrouted and never reported as healthy.

`priority` is an optional integer in `-20..19`, defaulting to zero for eligible routed evidence. `frequency_hz` is an optional finite number strictly above zero in Hz; absence means uncapped. In M1, both are permitted only on the exact EOS camera → gate route above. EGIA-local, bridge and descriptive edges reject explicit QoS until their owners publish exact eligible routes. Fixed safety, actuator, result, health, latch, and stop routes reject either field and cannot be capped or silently dropped. Command-shaped ports and generic package contributions cannot create a second actuator route; the exact Dispatcher binding remains mandatory. IsOS validates the declared route without scheduling or claiming live health. EOS's [owner edge contract](https://github.com/Island-Team/Island-eos/blob/refactor%28v2%29/runtime-main/docs/eos/interfaces/hardware.md#g06-typed-edge-admission) validates its EOS projection independently; IsOS must reject a full-graph violation before any owner setup render or graph write.

Other negative fixtures must name exact source pointers for wrong type/unit, unknown port/path, placement, cardinality, transport, cross-core bridge, cycle, priority bounds, non-finite/zero rate, QoS on fixed or unrouted edges, and actuator bypass. Each rejection must leave saved bytes and active revision unchanged. The same fixture should produce the same edge diagnostic through HTTP Validate and Apply, CLI Apply, and migration preflight; Run and Restart must reject a tampered saved graph before child spawn.
