# Verified package admission

[中文](../../../docs_cn/isos/interfaces/package-verification_cn.md)

**P01 owner contract — implemented.** IsOS owns package installation, receipts, release snapshots and package admission. The CLI, loopback API and graph preparation call the same verifier. EOS receives only paths selected from a verified exact package pin; it does not install or trust a package sidecar independently. The [v4 release envelope](releases.md) defines distribution fields. This contract defines the local verification boundary for that envelope, without defining MuJoCo scene/device semantics (P02) or selector options (P03).

## Invocation and result

`isos pkg install ID --version VERSION`, `isos pkg install --manifest RELEASE --asset ARCHIVE --allow-unapproved`, and `isos pkg link ID VERSION BUNDLE --manifest RELEASE` select one exact `{id,version}`. The equivalent loopback operations are `POST /api/isos/v1/packages/install` and `/link`; `isos pkg verify RELEASE ARCHIVE` checks without publishing. An approved catalog response is still parsed and verified as v4 metadata. A local candidate needs `--allow-unapproved`. A link with no `--manifest` discovers `<bundle>/release.json` as before; a valid v4 manifest there produces a verified link. Only a link with neither explicit nor discovered v4 manifest is `unverified_legacy_link`, listed for inspection and removal but inadmissible for Apply, migration commit, Run or Restart under either graph version. Saved legacy graph bytes remain readable and unchanged. No command changes saved graph bytes, saved revision, active revision, or child processes.

On success, IsOS atomically publishes one private `data/packages/<namespace>/<name>/<version>/` directory. Installed archives contain a copied payload; a link contains verifier-owned metadata and the canonical external source path. A linked source remains mutable, so its frozen fingerprint is rederived before every Apply and Run. No operation silently refreshes a changed receipt. Replacing an exact version requires explicit removal after no saved or active graph references it, then a fresh install/link. A failed operation removes staging, publishes no partial receipt or sidecar, and leaves all graph/process state unchanged.

The receipt is a versioned JSON object. Its public fields are:

| Field | Type / unit | Purpose, default and validation | Compatibility |
| --- | --- | --- | --- |
| `schema_version` | integer / — | Required `2` for a P01 verified receipt. | Existing `1` is readable as unverified until explicitly reinstalled or relinked. |
| `id`, `version` | strings / — | Required exact v4 release and store-key identity; reject path separators in version and noncanonical package IDs. | Never infer a latest version. |
| `source_kind` | `approved_catalog`, `local_candidate`, or `local_link` / — | Required provenance of the accepted metadata and payload. | A legacy receipt lacking this field is unverified. |
| `source_commit` | 40-hex string / Git commit | Required from the v4 manifest; records source provenance, not proof of installed bytes. | Must equal the frozen release. |
| `asset_sha256` | 64-hex string or null / SHA-256 | Required for an archive, matching the selected platform asset; null only for a link. | A link uses `payload_sha256` instead. |
| `release_sha256` | 64-hex string / SHA-256 | Digest of the canonical verifier-owned release snapshot. | Recompute at Apply and Run. |
| `payload_sha256` | 64-hex string / SHA-256 | Digest of the verified payload file tree, including descriptor, executable and assets. | Recompute from the installed or linked root at Apply and Run. |
| `sidecar_sha256` | 64-hex string or null / SHA-256 | Digest of the canonical `node-types.json` projection; null only when the release declares no contributions. | Recompute and compare with the release projection before loading. |
| `local_link` | absolute path or null / — | Canonical source root for a link; null for an installed archive. | The path itself is not executable authority. |

The payload digest is SHA-256 over the bytes `isos-package-tree-v1\0` followed by sorted UTF-8 package-relative entries. Each entry writes a little-endian `u32` path-byte length, path bytes, one type byte (`F` regular file or `D` directory), one executable-bit byte (`0` or `1`), a little-endian `u64` length (`0` for directories), and 32 raw SHA-256 bytes of file content (all zero for directories). Only the file's executable bit affects this digest; owner-only storage permissions are checked separately. No symlink, special file, duplicate normalized path or escaping path is accepted. An archive cannot contain reserved top-level verifier metadata names. For installed payloads, the verifier excludes only the metadata files it writes into the store (`receipt.json`, `release.json`, `node-types.json`); the release and sidecar have separate digests above. For linked payloads, every source-root file, including a source `release.json` or `node-types.json` if present, enters the tree digest; the verifier-owned copies live in the store directory and are checked separately. An explicit manifest outside the linked source is copied into the store; changing that original external file afterward is irrelevant because the accepted snapshot is the authority. Entries and total bytes remain bounded by the archive limits; hash with streaming reads. The canonical manifest and sidecar serialization is deterministic and shared by publication and revalidation. A local administrator able to replace all owner-owned files is outside this receipt's trust claim; the receipt detects accidental or partial mutation and binds all content to the exact release pin.

Before publication, check the selected asset's host OS, architecture and declared runtime selectors for either source. An archive install additionally checks its exact byte size and SHA-256 against that selected asset; a link has no archive bytes and records `asset_sha256:null`. Extract archives into a private staging directory, rejecting absolute paths, `..`, links, devices and duplicate entries. Validate the v4 release identity, kind, exact `@v0.1` or explicitly supported historical `@v1.0` contribution IDs, unique contributions and safety adapters, and declared descriptor/entrypoint references before writing the sidecar. `island/mujoco-sim` (or a release declaring the MuJoCo simulator contract) must contain a bounded `backend-v2.json` with matching `{id,version}`, a supported descriptor schema/protocol, a contained executable regular file with execute permission, and contained regular scene and referenced asset files. Other backend releases may be adapter-library-only; they need no MuJoCo descriptor unless they declare one. A declared adapter library must be contained and match its own SHA-256. Reject symlinks at every component of referenced paths, including a changed linked source; canonical-prefix checks alone are insufficient. P01 checks existence, containment and content integrity. P02 validates MuJoCo-specific scene IDs, device map, library availability and selectable resource descriptions.

Apply and Run revalidate receipt schema and pin, release digest and source commit, selected platform metadata, sidecar bytes against the release projection, payload tree digest, descriptor and every referenced path before any owner setup, generated snapshot publication or child spawn. A changed source payload, installed payload or verifier-owned release snapshot returns `package_changed` at `payload` or `manifest`; a sidecar mismatch returns `package_invalid_sidecar` at `sidecar`; a new symlink or escape returns `package_unsafe_path` at the containing stage. All require explicit reinstall/relink after reference checks. The graph remains a declaration; a package-contributed node cannot authorize an actuator route or executable launch beyond registered placement and dispatcher admission.

The pin collector covers `node.package`, `node.adapter.package`, and the historical paired `node.settings.package` plus `node.settings.version` form. The canonical `{id,version}` set is shared by package revalidation, owner setup `packages`, sidecar selection, Apply, Run and Restart; malformed or incomplete pins fail at their node path. `node_sets::list/compose`, backend discovery, package listing and preview-link also consume verified handles: corrupted metadata cannot become a ready catalog row or a composed node-set preview. Discovery may show it as unavailable with a sanitized reason. CLI and HTTP listing rows carry `status` (`verified`, `unverified_legacy_link`, or `unavailable`), Boolean `available`, and a sanitized `reason`; verified rows retain `source_kind` provenance. Only pins referenced by the candidate or saved graph participate in its admission. An unrelated installed package may appear in discovery with an unavailable reason, but cannot inject a sidecar into that graph or block its Apply/Run. Runtime catalog discovery must not treat an arbitrary file found by a store-wide sidecar scan as verified authority.

The CLI returns nonzero on failure. HTTP retains the existing schema-1 `{schema_version,ok,data,error}` envelope: `error` is a sanitized string, and on P01 failures `data.diagnostics` adds a bounded classification array. Verification/admission returns `422`; an exact-version collision or referenced removal returns `409`. A diagnostic has `code` (string / —), `path` (JSON Pointer or empty string / —), `message` (string / —), `id` and `version` (exact strings / —), and `stage` (bounded string / —); all are required, with no arbitrary extras. `code` is one of `package_platform_mismatch`, `package_digest_mismatch`, `package_invalid_manifest`, `package_unsafe_path`, `package_missing_file`, `package_invalid_descriptor`, `package_invalid_sidecar`, `package_changed`, or `package_version_exists`. `stage` is `manifest`, `asset`, `extract`, `descriptor`, `payload`, `sidecar`, or `admission`. `path` points to the graph pin during Apply/Run, or is empty for a direct package operation. Messages identify the corrective action and exact package pin, without local source paths, download stderr, secret values, raw manifest content, or arbitrary environment data. The package log event carries this code, exact identity, source kind and available digest/commit provenance, plus manager-session correlation IDs; it does not include a raw error chain.

For example, `POST /api/isos/v1/packages/link` accepts `{ "id": "island/mujoco-sim", "version": "0.1.1", "path": "/home/user/bundle", "manifest": "/home/user/bundle/release.json" }`. Success retains the existing `data.path` and `data.installed` fields and adds `data.verified:true` and `data.source_kind:"local_link"`; `installed` contains the new schema-2 receipt for this exact pin. A changed linked executable reports `{ "schema_version": 1, "ok": false, "data": { "diagnostics": [{ "code": "package_changed", "path": "/cores/eos/layers/process/groups/mujoco/nodes/sim/package", "message": "Reinstall or relink island/mujoco-sim@0.1.1", "id": "island/mujoco-sim", "version": "0.1.1", "stage": "payload" }] }, "error": "Reinstall or relink island/mujoco-sim@0.1.1" }`; Apply and Run preserve saved and active revisions.
