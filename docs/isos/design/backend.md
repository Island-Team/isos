# IsOS-owned backend packages

[中文](../../../docs_cn/isos/design/backend_cn.md)

MuJoCo is the first Aether backend bundle: `island/mujoco-sim@0.1.1`. A bundle contains `backend-v2.json`, `bin/eos-mujoco-sim`, scenes, and assets. The descriptor filename is a current package compatibility identity. The release manifest describes distribution and archive verification. The backend descriptor describes executable, scene IDs, device IDs, protocol, and runtime dependency. The current `1.0.0` graph uses the package-contributed `eos.process.mujoco@v1.0` node; the `0.1.0` writer uses `@v0.1`. These have separate jobs so package installation cannot silently edit a deployment.

IsOS resolves the exact pinned receipt at validate, apply, and run. Local links are reread on every resolution. It checks the descriptor identity, executable permission, selected scene, referenced scene assets, required MuJoCo library, canonical socket path, and EOS adapter device/socket references. A fingerprint of the descriptor, executable, scene, and referenced assets detects changes to a running linked package. The user edits scene selection in the graph and explicitly applies it. IsOS passes the verified executable and scene paths to EOS at launch. EOS reads the graph, starts MuJoCo as its child, and connects typed camera/base/manipulator adapters to the simulator socket. EOS cannot install packages or change the applied graph.

The socket is below the owner-only IsOS runtime directory. IsOS starts the EOS runtime first; EOS starts MuJoCo and waits for its socket before admitting hardware operations. IsOS owns the EOS, bridge, and config child handles; EOS owns the simulator child. Stopping EOS terminates MuJoCo, and an unexpected simulator exit fails EOS so IsOS can restart the whole component. A backend can be removed only after no applied graph references its exact package ID and version. Later backend packages can use the same out-of-process resolver boundary; actuator types still pass EOS safety admission.

**0.x target:** IsOS resolves stable scene and device IDs through verified package metadata and the [setting-options API](../interfaces/local-api.md#release-target-setting-options--not-implemented). EOS keeps its compiled MuJoCo socket adapter in an internal adapter registry; the external simulator package remains installed by IsOS. EOS must reject an adapter family absent from its compiled registry, even when a package advertises it. IsOS records an exact package pin and validated generated config; it does not copy the simulator into EOS or allow package code to add a second actuator route. See the [admission, run and stop algorithms](system.md).

**P02 implementation.** Consume only P01's exact verified package handle. Classify `backend-v2.json` by `catalog_version`: the complete old shape remains legacy-only, the complete `0.1.0` shape publishes scene/device metadata, and a partial or unknown shape fails closed. For each selected scene, compare the declared profile to a safely parsed MJCF marker and required model elements, compare SHA-256 to the verified XML bytes, then check each generic EOS adapter's selected device ID, kind and `scene_ids` membership. The P01 payload digest covers referenced assets; an altered sealed payload fails there before semantic P02 errors. Check `MUJOCO_ROOT` library availability before Apply and launch, and confirm the actually loaded version at readiness. The [IsOS contract](../interfaces/mujoco-catalog.md) and [owner fixtures](../../../tests/fixtures/scene_catalog/README.md) define exact fields, paths and ordering.

The descriptor parser accepts the additive target fields, and the node-set composer requires graph `0.1.0` for the new preset while retaining legacy `1.0.0` sets. Keep the historical parser path and safe old graph behavior distinct: a legacy descriptor cannot publish the new preset even if its current sidecar contains one. Compose only a draft using the package process type plus generic EOS camera/base/manipulator, primitive-binding and gate types. For each generic hardware adapter, require `simulator_node == device_id ==` its selected device ID, while its backend reference identifies the process node. Do not duplicate the starter Dispatcher or add a Vision identity. The P01 cross-repository CLI fixture uses the owner-provided `@v0.1` process identity without duplicating it. P03 separately owns generic node-options presentation.

`isos init` writes a starter graph once. Home reports installed/linked bundles, scene and prerequisite issues, saved versus active revision, run status, and logs. Graph edits the one shared IsOS/EOS/EGIA graph. EGIA common nodes are design-only until their runtime exists. Visual layout is separate from runtime configuration.

## Development check

Use a fresh `ISOS_HOME` and run `isos init --mode dev`, build EOS and IsosUI in their own repositories and configure their paths, then start `isos serve`. Link a staged bundle with `isos pkg link island/mujoco-sim 0.1.1 <bundle> --manifest <bundle>/release.json`, preview its `sim-hardware` node set, then run `isos config validate <graph>`, `isos config apply <graph>`, and `isos run`. Use `isos deployment stop` for a graph-only stop and `isos stop` to shut down the manager and all owned children. Set `MUJOCO_ROOT` to the installed MuJoCo runtime. The EOS `aether-profile` validator and Rust executables must be available. See [node fields](../interfaces/node-graph.md) and [package commands](../usage/packages.md).

For the graph-run recovery change, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test` passed (69 tests). `cargo build && python3 tests/clean_home.py` passed the IsOS→EOS→mock MuJoCo lifecycle scenario. The fixed-workload socket baseline on this host was 98.9 requests/s, 10.102 ms median, and 11.210 ms p99. Complete output is in the local ignored `logs/test/20261031-graph-run-recovery/` directory.

For P02, run `cargo fmt --all -- --check`, `cargo clippy --all-targets --no-default-features -- -D warnings`, `cargo test --no-default-features`, `cargo build --no-default-features`, `python3 tests/package_verification_cli.py`, and `python3 tests/scene_device_catalog_cli.py` from the IsOS checkout. The last command builds the real owner bundle, links it in isolated homes, previews the `0.1.0` set, validates and applies it, launches the real simulator, and checks wrong scene/device, missing library, incomplete catalog and sealed payload failures. It requires the built EOS Rust binaries, MuJoCo simulator binary, MuJoCo 3.16.0 installation, and local IsosUI build described in the test header. On 2026-11-01 the Cargo gates passed (108 unit tests plus 15 integration tests), the P01 clean-home replay passed 7 cases, and the P02 real-bundle replay passed 4 cases in 103.643 seconds. Full output is under local ignored `logs/test/20261101-p02-scene-device-catalog/`. This run measures correctness, not throughput or latency.
