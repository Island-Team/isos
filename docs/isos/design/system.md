# IsOS 0.x architecture and algorithms

[中文](../../../docs_cn/isos/design/system_cn.md)

**Target design; not implemented as a whole.** IsOS `0.1.0` is the owner of the saved deployment graph, exact packages, generated configuration, local workbench, and direct EOS/EGIA component children. EOS `0.2.0` owns hardware admission, the Rust runtime and its MuJoCo child. EGIA `0.1.0` owns agent stages. IsosUI `0.1.0` edits drafts through IsOS and presents status. Model-like services remain separate, explicitly started IsOS services. Current commands and behavior are described in [first use](../usage/get-started.md); target data contracts live in [graph](../interfaces/node-graph.md), [local API](../interfaces/local-api.md), [packages](../interfaces/releases.md), and [configuration/logs](../interfaces/configuration.md).

```text
registry/catalog → verified release receipt → node types, sets, assets
                                           ↓
user draft → IsosUI/CLI → IsOS validate → revision-checked Apply → saved graph
                           ↓                   ↓
                    resolved selectors     immutable core config
                                               ↓
                          IsOS manager → EOS Rust → MuJoCo child/socket
                                       → EGIA Python stages
                          status/log cursors → IsosUI work panels
```

The graph is `core → layer → group → node`; a registered type fixes placement, capabilities, settings, typed ports, lifecycle and description. Instances fix identity, operator description, package pin and values. A package may contribute nodes without gaining authority to run arbitrary commands. IsOS owns verification and configuration; EOS owns an **internal adapter registry** for compiled implementations such as MuJoCo. The simulator executable and scene remain an external, exact-version IsOS package. EOS reads the applied graph and generated snapshot but never installs packages or edits the graph. One EOS dispatcher admits every actuator command, including those sent through package adapters.

## Admission and Apply algorithm

1. Read graph bytes and calculate SHA-256 revision before any normalization. Select the parser from the graph version. For the target reader, accept newly authored `0.1.0` and existing safe `1.0.0` graphs; reject unknown future versions. Normalize omitted optional descriptions and edge defaults **in memory only**.
2. Ask each enabled core to validate its subtree and type IDs. Merge built-in types with verified package sidecars; reject duplicate IDs, unregistered placement, incompatible typed ports and unsupported codecs. Preserve existing `@v1.*` IDs where registered. Never execute legacy arbitrary `command` nodes.
3. For every exact package pin, verify receipt, release manifest, executable, descriptor, scene and referenced assets. Resolve selector IDs to verified assets; an unavailable selected ID fails Apply with node/setting path. Validate simulator device IDs, socket ownership and adapter compatibility. The graph stores stable IDs and pins, not absolute asset paths.
4. Compare the caller's expected revision with the saved revision. For a new `0.1.0` draft, serialize canonical bytes and calculate their new SHA-256; for an unchanged legacy graph, retain its original bytes and revision. Render bounded EOS/EGIA setup files from those bytes, write private temporary files, and atomically publish a snapshot under the **new** revision. Check the expected saved revision again before atomically saving new draft bytes. An unused snapshot from a losing concurrent edit is safe to discard. Return the resulting revision; active children retain their previous revision until explicit Restart.

The explicit migration operation previews old-to-new graph and type changes, requires the original revision, and returns a new revision. It preserves a legacy graph's bytes until accepted. A failed parse, package check, render, or revision comparison leaves the saved graph and active processes unchanged.

## Run, stop and recovery algorithm

Run re-reads the saved bytes, package receipts, selected assets, configured core executables and generated snapshot identity. It validates version support against each core's advertised arrays. IsOS starts direct component children in dependency order and waits for readiness; EOS starts its MuJoCo child, connects its owner-only Unix socket and constructs declared adapters. EGIA starts only after its required EOS gateway capabilities are healthy. TCP listening alone is insufficient as EGIA readiness. On failure, IsOS stops dependents before providers, reports the last error and emits one state-change event. Stop tells EOS to stop admitted actuators before EOS terminates MuJoCo; IsOS then stops component process groups in reverse dependency order with bounded TERM/KILL grace. Restart failure restores previous specifications when possible and otherwise marks the deployment degraded.

A linked package may change on disk, so its fingerprint is checked at Apply and Run. An active process never hot-swaps binaries or scene bytes. Removal rejects a package pinned by saved or active deployment. Independent services have their own explicit lifecycle and never become hidden graph dependencies.

## Selector and wire algorithms

For each registered `Setting.selector`, identify its provider (`package`, `registry`, or `graph`), then derive options for the **draft** graph. Package provider reads only the verified exact pin. The result is grouped by node path and setting key; it includes stable IDs, labels, descriptions, availability and reasons. Preserve an unavailable selected value visibly so the operator can repair it. Apply re-resolves all selections. IsosUI's searchable control resembles a model-weight chooser but stores a stable ID, not a file path.

IsOS validates each edge's source, destination type, `priority` and `frequency_hz`. **Current implementation:** the editor validation API compares the exact registered port data type and returns an edge-addressed `edge_type_mismatch` diagnostic before Apply; the data type's schema carries the field units. Other validation failures still use the EOS validator's general diagnostic. EOS owns routed delivery in the target: a monotonic per-edge token bucket caps updates; weighted fair service and bounded queues prevent high-priority streams from starving others; overflow is counted and logged at a bounded rate. `expected_rate_hz` is producer metadata and never silently becomes an edge cap. A design-only edge is visible in IsosUI but has no claimed runtime scheduler. Priority cannot bypass dispatcher safety or actuator stop.

### G03 migration transaction

The [graph contract](../interfaces/node-graph.md#g03-explicit-graph-migration) owns the exact type map; the [local API](../interfaces/local-api.md#g03-migration-routes) owns request and response fields. The migration engine is shared by HTTP and CLI. It keeps the original `SavedGraph` bytes and SHA-256 separate from a parsed value and a proposed value, so a preview never changes the source. It applies only version and table-driven type substitutions, then checks that every other accepted JSON value is equal. It refuses unknown fields instead of losing them through typed deserialization. A mapped type still needs exact registration, settings, package provenance, placement, and port compatibility; type suffixes are never inferred.

Preview may compute a proposal while a dependency is unavailable, but marks it blocked. Commit repeats all checks against current bytes under the graph lock and requires both the original revision and the proposed digest. The 0.1 readiness barrier includes IsOS-owned component registration, EOS setup and runtime support for the projected EOS core, EGIA setup support for any present legacy common nodes, and graph-wide cross-core edge and reference admission. Until G06 supplies that full admission, a graph with cross-core links cannot migrate. EOS's setup identity must not advertise a graph version that its launched runtime cannot consume. IsOS passes the revisioned EOS-only generated projection to that runtime; it does not let runtime reparse the unvalidated full graph after migration.

The publication point is the atomic rename of the staged graph file. Before that point, immutable generated files, receipt fingerprints, and their manifest have been validated, fsynced, and published under the proposed revision; the source revision is rechecked under lock. If preparation fails, remove temporary files and keep the old graph. A detached unused snapshot is harmless and can be collected. The graph parent directory is fsynced after rename; failure there has an uncertain commit outcome, resolved by rereading the saved revision. There is no setup or launch step after graph rename. Active children remain on their old revision and are changed only by explicit Restart. A crash or lost reply after rename is resolved by a fresh GET and comparison with the preview digest; retrying with the old revision cannot apply twice.

The implementation must exercise byte-level no-write assertions for preview, stale source, changed package fingerprint, unknown/unsafe type, render failure, and failed snapshot/graph publication. A success test checks the exact fixture mapping and preserved pins/fields, saved versus active revision separation, Run/Restart preflight, and old graph recovery after a failed transaction. Save complete logs under `logs/test/<run-id>/` and replay the HTTP and CLI boundary with a clean `ISOS_HOME` before the G03 branch is merged.

The new writer uses `data/generated/<deployment>/<saved-revision>/` as an immutable lookup key for `0.1.0`; Run and Restart validate its manifest and substitute the verified `eos/graph.json` into EOS runtime and config-server `--profile` launch arguments without changing saved `settings.args`. They never follow a mutable `current` pointer or the old flat generated directory. The old flat `core-setup/launch-inputs.json` remains only for `1.0.0` compatibility. Init and missing-graph GET produce a `0.1.0` starter; changed new-version PUT and CLI Apply use the same revision compare-and-swap engine. The owner-scoped validator uses IsOS-owned process definitions, EOS setup projection, EGIA setup, and IsOS graph-wide links; it does not feed IsOS `@v0.1` nodes to EOS whole-profile validation.

Run and Restart also compare every stored generated file with a fresh owner render of the exact saved graph. A modified file plus a modified manifest digest is rejected. A rebuilt core binary makes the snapshot's launch inputs stale. `isos init` reports the stale input and leaves the immutable snapshot untouched; restore the pinned binary or create a new graph revision and Apply. A separate generation identity for refreshing unchanged graph bytes belongs to P04/P05.

G03 implementation evidence (2026-11-01): with EOS `fb57a0c5` debug binaries at `/home/ashex/projects/Island-eos/target/debug` and fresh `ISOS_HOME` directories under `logs/test/2026-11-01-g03/`, `cargo fmt --all -- --check`, `cargo clippy --all-targets --no-default-features -- -D warnings`, and `cargo test --all-targets` passed (87 unit and 5 CLI tests). ### G06 full-graph edge admission — target design

Build one immutable admission view from the exact graph revision and exact registered owner catalogs. Walk nodes in canonical path order and each declared input source in its authored order; resolve both endpoint descriptors before checking the edge. Record the actual JSON Pointer for object or array shape before normalization. Check exact type, unit schema identity, transport, cardinality, required input, duplicate source and cycle rules, then classify the route against an explicit owner route table. IsOS checks cross-core bridges and references that EOS's owner projection cannot see. Keep process dependencies in the same full-graph preflight but outside the data-edge route table. A missing owner descriptor or bridge declaration fails closed with the original pointer. Do not forward EOS's older prose profile error as the IsOS edge diagnostic; it may lack a pointer. The [graph contract](../interfaces/node-graph.md#g06-graph-wide-edge-admission--target-contract) defines fields and safety rules.

Validate returns the ordered edge inspector list only after the entire graph passes. Apply and migration commit run this admission before owner render and before publishing any snapshot or graph bytes. Run and Restart repeat it against saved bytes and verified snapshot before child spawn, so a changed package descriptor or tampered graph cannot reuse an old admission decision. Legacy `1.0.0` reads retain the established path and bytes. Tests replay the same negative fixture through HTTP, CLI, migration, and launch preflight, asserting identical pointer/code and unchanged saved/active revisions. G06 publishes declarations only; EOS R01 and EGIA A04 later prove live delivery, bounded queues, and gap counters.

Independent design reviews by the IsOS implementation agent and EOS edge-contract owner accepted the M1 route table and fixed-path metadata on 2026-11-01. They confirmed that the camera frame → gate frame pair is the sole eligible M1 evidence route, that the Vision bridge remains closed pending a registered `0.1.0` destination, and that IsOS must generate its own pointer diagnostics for errors caught by EOS's older prose validator.
