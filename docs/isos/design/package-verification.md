# P01 package verification design

[中文](../../../docs_cn/isos/design/package-verification_cn.md)

**Target design — not implemented.** The [verified package contract](../interfaces/package-verification.md) owns the receipt fields, commands and failures. This page explains the verifier and transaction. The existing release parser verifies v4 shape and archive digest, while backend resolution fingerprints only part of a bundle. The current link can omit a manifest, and sidecar lookup trusts file existence. P01 closes these boundaries before P02 adds scene/device choice semantics.

## Publication transaction

Take the package lock, validate an exact release and platform asset, then create a private sibling staging directory. For an archive, stream the asset into staging with the selected asset's size and SHA-256 limit, reject unsafe or repeated entries, and set owner-only permissions. For a link, canonicalize the source root once and verify every path component without following a symlink. Run one payload verifier over both roots: validate the backend descriptor's identity/protocol and all referenced contained regular files, executable bit, declared adapter digests, activation template sources and package contribution structure. Compute a deterministic whole-tree digest and generate the sidecar solely from the accepted release object. Write the release snapshot, sidecar and receipt with separate digests, fsync their files and staging directory, then atomically rename staging to the absent exact-version target and fsync its parent. Any failure before rename removes staging; no graph or process handle is acquired by package publication.

The linked source stays at its original path for developer builds. The published receipt freezes a content digest and canonical root, rather than pretending the external tree is immutable. Revalidating a changed link returns a stable `package_changed` diagnostic; relinking is a deliberate replacement operation after reference checks. Installed payloads also get a tree digest, so mutation after extraction is detected. The content walk rejects symlinks and special files in all directories, verifies path components before open, and compares file identity around streaming reads to reduce rename races. Tests include a concurrent source replacement and a directory symlink inserted after link. This is local integrity, not a claim of protection against the owner replacing every metadata file.

## Admission order

Before selecting a sidecar, collect exact pins from all supported graph shapes once and reject malformed pairs. For each referenced pin, load receipt and release under a shared package lock, rederive all three digests, verify the descriptor/reference closure, and return a verified handle containing canonical payload root, accepted release and generated sidecar path. Pass only those handles to core setup, node-set composition, backend discovery and EOS launch projection. Apply, migration commit, Run and Restart invoke this before owner render or spawn; Validate and preview may return the same package diagnostics without mutation. Package listing scans store entries but marks malformed or legacy receipts unavailable rather than making them runtime inputs. A global catalog can inspect installed packages, yet a graph's sidecars must be exactly its verified pin set.

The existing backend fingerprint can remain a launch input for selected scene content, but cannot replace the release/payload/sidecar proof. P02 adds semantic checks for stable scene/device IDs, the MuJoCo runtime library and selector descriptions. P03 resolves setting options; neither changes P01's exact-pin integrity rule.

## Evidence

The [frozen P01 cases](../../../tests/fixtures/package_verification/README.md) cover a clean-home verified link and archive install; platform, size and digest mismatch; missing manifest; duplicate archive entry; descriptor identity and executable failures; symlink and path escapes; sidecar mutation; linked and installed payload mutation; unrelated corrupt package isolation; and failure atomicity. Unit tests exercise the verifier with bounded temporary files. CLI/HTTP integration tests repeat the same failures at install/link, Apply and Run, asserting exact pin and stage but no local path leakage. A running deployment keeps its old active revision when a package fails revalidation. Save full format, Clippy, test and clean-home output under `logs/test/<run-id>/`, and record commands/results in this page after implementation review.
