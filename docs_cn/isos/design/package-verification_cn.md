# P01 软件包验证设计

[English](../../../docs/isos/design/package-verification.md)

**目标设计——尚未实现。** [已验证软件包契约](../interfaces/package-verification_cn.md)负责收据字段、命令及失败；本页说明校验器与事务。现有发行解析器检查 v4 结构与归档摘要，而后端解析只对包的一部分计算指纹。当前链接可省略清单，侧车查找只看文件是否存在。P01 在 P02 增加场景／设备选择语义前关闭这些边界。

## 发布事务

取得软件包锁，验证精确发行和平台资产，然后创建私有同级暂存目录。归档安装流式读取资产并检查选定资产的大小和 SHA-256，拒绝不安全或重复的归档项，设置仅所有者权限。链接时规范化来源根目录一次，并在不跟随符号链接的情况下检查每个路径组成部分。两种来源共用载荷校验器：检查后端描述的身份／协议、引用的包内普通文件、程序执行位、声明的适配器摘要、激活模板来源及包贡献结构。计算确定性的整个文件树摘要，仅从接受的发行对象生成侧车。写入发行快照、侧车与带独立摘要的收据，对文件和暂存目录 fsync，再原子 rename 到尚不存在的精确版本目标并 fsync 父目录。rename 前失败清理暂存；发布软件包不取得任何图或进程句柄。

开发构建的链接来源仍留在原处。已发布收据冻结内容摘要及规范根目录，不把外部目录误称为不可变。变化的链接在复查时返回稳定的 `package_changed`；检查引用后才能有意替换。安装载荷也有文件树摘要，解压后变化会被发现。文件树遍历拒绝所有目录中的符号链接及特殊文件，在打开前检查路径组成部分，并在流式读取前后比较文件身份以降低 rename 竞态。测试包含并发替换来源及链接后插入目录符号链接。这是本机完整性，不宣称能防止所有元数据都被替换的归属方用户。

## 准入顺序

选择侧车前，从所有受支持图形状一次收集精确固定版本，并拒绝不完整的成对字段。对每个被引用的固定版本，在共享软件包锁下读取收据与发行，重新计算三个摘要，检查描述／引用闭包，返回包含规范载荷根目录、接受的发行和生成侧车路径的已验证句柄。仅将这些句柄交给 core setup 和 EOS 启动投影。Apply、迁移提交、Run 及 Restart 在归属方 render 或启动前调用；Validate 和预览可无副作用返回相同软件包诊断。软件包列表可扫描库，但把损坏或旧收据标为不可用，不当作运行时输入。全局目录可检查已安装包，但某个图的侧车必须恰好来自其已验证固定版本集。

现有后端指纹可继续作为所选场景内容的启动输入，但不能代替发行／载荷／侧车证明。P02 增加稳定场景／设备 ID、MuJoCo 运行库和选择器说明的语义检查。P03 解析设置选项；两者都不改变 P01 的精确固定版本完整性规则。

## 证据

[冻结的 P01 用例](../../../tests/fixtures/package_verification/README.md)涵盖干净主目录的已验证链接和归档安装；平台、大小及摘要不匹配；缺清单；重复归档项；描述身份及程序失败；符号链接和路径逃逸；侧车变化；链接和安装载荷变化；无关损坏包隔离；以及失败原子性。单元测试用有界临时文件检查校验器。CLI／HTTP 集成测试在安装／链接、Apply 与 Run 重放相同失败，断言精确固定版本和阶段且不泄露本机路径。包复查失败时，运行中的部署保留旧活动修订。完整格式、Clippy、测试及干净主目录输出存入 `logs/test/<run-id>/`，在实现审查后于本页记录命令和结果。
